## 문제

- 리뷰어가 PR마다 같은 지적을 반복하느라 설계 논의가 뒤로 밀림
- 그 사이 기능 패키지끼리 서로 참조하는 순환과 다른 기능의 Repository를 직접 부르는 코드가 쌓임

## 원인

- 문서와 skill에 팀 컨벤션을 적어 두었지만 AI가 만든 코드는 계층 방향과 클래스 이름, 위치 규칙을 계속 어김
- 컨벤션이 글로만 있어 어겨도 머지를 막는 장치가 없었음

## 고려한 방법

- **문서와 skill을 더 자세히 씀**: 이미 적어 둔 규칙도 AI가 매번 지키지 않았으므로 같은 일이 반복됨
- **AI 리뷰봇이 PR마다 지적**: CodeRabbit을 이미 쓰고 있었지만 지적만 할 뿐 머지를 막지 못하고 매번 같은 기준으로 판단한다는 보장이 없음
- **컨벤션을 ArchUnit 테스트로 옮겨 CI에서 검사**: 기계로 판단할 수 있는 규칙은 매번 같은 기준으로 머지를 막을 수 있음

## 선택과 이유

- **컨벤션을 문서 대신 ArchUnit 테스트로 옮김.** 이름, 위치, 의존 방향은 사람이 판단할 필요가 없는 규칙이라 리뷰어가 아니라 테스트가 맡는 것이 맞다고 봄
- 팀원 1명과 함께 규칙 13개를 만들었고 의존 방향 4개, 이름과 위치 5개, 작성 규칙 4개로 나눔
- 규칙을 PR CI의 `gradlew check`에 넣어 `dev-be`와 `release-be`로 가는 모든 PR에서 돌게 함
- 규칙을 켜며 드러난 순환 참조와 Repository 직접 호출은 같은 PR에서 각 기능의 Service를 거치도록 고침

## 감수한 것

- 이름, 위치, 의존 방향처럼 기계로 판단할 수 있는 규칙만 잡히고 책임을 어디에 둘지는 계속 리뷰에서 정함
- 규칙을 켜는 PR 하나에서 85개 파일을 함께 고쳐 한 번에 리뷰할 변경 범위가 커짐
- **규칙이 제대로 잡는지는 PIT 변이 검사로 확인하려 함.** 코드를 일부러 바꿔 테스트가 잡아내는지 보는 검사를 변경한 클래스에 붙였지만 아직 실제 PR에서 돌려 보지 못함

## 결과

- 규칙에 담긴 지적은 리뷰어 대신 CI가 하고 위반 코드는 머지 전에 실패함
- 도입 PR에서 85개 파일을 고쳐 기능 패키지 사이 순환 참조를 없앰
- 이후 AI 챗봇을 붙이며 대화 서비스가 Spring AI 타입에 직접 의존하지 못하게 막는 규칙을 혼자 추가함. 현재 규칙은 16개
