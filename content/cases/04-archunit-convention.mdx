- **문제**: 백엔드 PR(Pull Request)마다 다른 기능의 Repository를 직접 주입받거나(`UserDeletionService`의 4개 Repository 직접 참조) 기능 간 순환 의존이 생기는 문제(`catalog ↔ checklist`, `appointment ↔ checklist`)가 반복되어 리뷰어가 매번 눈으로 확인하고 같은 원칙을 설명해야 했습니다.
- **본인 행동**: 문서에 있던 팀 컨벤션 중 코드로 판별 가능한 항목을 `ArchitectureConventionTest`의 ArchUnit 규칙 13개로 작성해 로컬 테스트와 PR CI(Continuous Integration)에 연동하고, 규칙이 드러낸 `appointment`와 `checklist`의 순환 의존을 해결하기 위해 두 기능을 단일 경계로 통합했습니다.
- **결과와 도입 비용**: 타 기능 내부 구현 참조를 PR 생성 전 로컬 테스트에서 즉시 차단해 리뷰의 초점을 기계적 의존 확인에서 Service 책임·비즈니스 규칙 논의(예: [PR #421 어댑터 위치 논의](https://github.com/woowacourse-teams/2026-bibbidi/pull/421#discussion_r4237282779))로 옮겼습니다. 다만 기존 위반을 한 번에 정리하느라 도입 PR에서 85개 파일을 수정하는 초기 비용을 치렀으며, 리뷰 시간이나 수정 요청 횟수의 감소 폭은 별도로 측정하지 않았습니다.

### 문제와 원인: 문서에만 있고 코드로 검증되지 않던 팀 컨벤션

비비디(Bibbidi)는 결혼 준비 일정을 관리하는 서비스입니다. 초기 MVP(Minimum Viable Product, 최소 기능 제품)를 빠르게 구현하면서 일정(`appointment`), 체크리스트(`checklist`), 카탈로그(`catalog`), 사용자(`user`) 기능을 각각 패키지로 나누어 개발했습니다. 팀에는 계층 간 의존 방향과 클래스 작성 방식에 관한 컨벤션 문서가 있었지만 Java 컴파일러와 기능 테스트는 아키텍처 규칙 위반을 오류로 잡지 못했습니다.

그 결과 백엔드 PR 리뷰에서 동일한 구조 위반을 사람이 반복해서 지적해야 했습니다.

- **타 기능 영속성 직접 참조 ([회원 탈퇴 PR #42](https://github.com/woowacourse-teams/2026-bibbidi/pull/42#discussion_r3885559907))**: `UserDeletionService`가 4개의 Repository를 직접 주입받고 체크리스트 데이터의 삭제 순서까지 알고 있었습니다. 체크리스트의 영속성 구조가 바뀔 때 회원 탈퇴 코드까지 고쳐야 하므로 데이터 삭제 책임을 해당 도메인으로 돌려야 한다고 리뷰했습니다.
- **기능 간 순환 의존 ([준비 항목 추가 PR #35](https://github.com/woowacourse-teams/2026-bibbidi/pull/35#discussion_r3876886468))**: `catalog`가 `checklist`의 JPA(Java Persistence API) Repository를 참조하고 반대로 `checklist`는 `catalog`의 Service를 참조해 순환 의존이 발생했습니다.

당시 저장소의 스타가 10개 미만이라 [연동해 둔 CodeRabbit 자동 리뷰도 동작하지 않았습니다](https://github.com/woowacourse-teams/2026-bibbidi/pull/94#issuecomment-5580276077). 기계적으로 판별할 수 있는 의존 규칙은 테스트 도구에 맡기고 사람은 설계 의도와 비즈니스 로직에 집중할 수 있는 장치가 필요했습니다.

### 선택: Spring Modulith 대신 ArchUnit을 사용한 이유

개인 프로젝트 ImHere에서는 Spring Modulith의 `ApplicationModules.verify()`로 내부 참조 위반 224건과 순환 의존 7건을 해결한 경험이 있었습니다([사례 1](/cases/module-boundary)). 그 과정에서 Spring Modulith가 내부적으로 ArchUnit을 사용한다는 점과 필요한 규칙만 직접 테스트 코드로 정의하는 방식을 파악하고 있었습니다.

비비디의 목표는 모듈 시스템을 새로 도입하는 것이 아니라 **기존 팀 컨벤션 중 코드로 판별 가능한 규칙을 빠르게 자동화하는 것**이었습니다. 백엔드 개발자 3명이 함께 작업하는 환경에서 당장 필요하지 않은 Spring Modulith의 모듈 공개 범위 제약까지 학습하고 적용할 필요는 없었기에, 기존 패키지 구조를 유지하며 팀이 합의한 규칙만 명시적으로 검사할 수 있는 ArchUnit을 선택했습니다.

### 구현: 기존 팀 컨벤션을 ArchUnit 규칙 13개로 코드화

팀 컨벤션 문서에서 코드만으로 위반 여부를 판별할 수 있는 항목을 추려 [`ArchitectureConventionTest.java`](https://github.com/woowacourse-teams/2026-bibbidi/blob/dev-be/BE/src/test/java/com/bibbidi/wedding/ArchitectureConventionTest.java)에 최초 13개 규칙을 작성했습니다.

| 분류 | 규칙 수 | 주요 검증 대상 |
| --- | --- | --- |
| 계층과 기능 간 의존 | 4개 | 계층 의존 방향, Domain의 독립성, 기능 간 순환 의존, 다른 기능 접근 방식 |
| 클래스 이름과 위치 | 5개 | Service, Repository, Controller, JPA Repository, Entity 명명 및 패키지 위치 |
| 작성 규칙 | 4개 | Lombok 사용 제한, `requireNonNull`, 예외 생성 헬퍼, `@RequestBody`와 `@Valid` |

#### 1. 계층 간 의존 방향과 기능 간 순환 의존 차단

Controller, Service, Repository, Persistence 네 계층 사이의 단방향 의존과 기능 패키지(Slice) 간 순환 참조 금지를 핵심 규칙으로 정의했습니다(실제 코드에는 Controller DTO(Data Transfer Object) 패키지 제외 조건과 `Domain` 패키지 독립성 규칙이 함께 포함되어 있습니다).

```java
@ArchTest
static final ArchRule 계층은_정해진_방향으로만_의존한다 =
        layeredArchitecture()
                .consideringOnlyDependenciesInLayers()
                .layer("Controller").definedBy("..controller..")
                .layer("Service").definedBy("..service..")
                .layer("Repository").definedBy("..repository..")
                .layer("Persistence").definedBy("..persistence..")
                .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
                .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller", "Service")
                .whereLayer("Repository").mayOnlyBeAccessedByLayers("Service", "Repository")
                .whereLayer("Persistence").mayOnlyBeAccessedByLayers("Repository", "Persistence");

@ArchTest
static final ArchRule feature_패키지_사이에는_순환참조가_없다 =
        slices()
                .matching("com.bibbidi.wedding.(*)..")
                .should().beFreeOfCycles();
```

#### 2. 다른 기능은 Service를 거쳐서만 접근하도록 강제

다른 기능의 내부 Repository나 영속성 구현을 직접 참조하지 못하도록 커스텀 조건(`다른_feature에_접근할땐_서비스만_거친다()`)을 작성해 대상 기능의 `service` 패키지를 통해서만 협력하도록 강제했습니다.

예를 들어 [`ChecklistService.java`](https://github.com/woowacourse-teams/2026-bibbidi/blob/dev-be/BE/src/main/java/com/bibbidi/wedding/checklist/service/ChecklistService.java)의 `changeItemCategory`는 카테고리 존재 여부를 확인할 때 `CatalogRepository`를 직접 부르지 않고 `catalogService.validateCategoryExists(categoryId)`를 호출하며, 기능 간 데이터 전달에는 `CatalogItemSnapshot` 같은 DTO를 사용합니다. 애너테이션과 일부 공통 패키지에는 예외를 허용해 타 기능 저장소 직접 참조를 막으면서 필요한 협력 경로를 유지했습니다.

### 예상보다 커진 리팩터링: 일정과 체크리스트의 기능 경계 재정의

ArchUnit 규칙을 처음 실행하자 단순한 import 수정이나 클래스 이동만으로 풀리지 않는 **일정(`appointment`)과 체크리스트(`checklist`) 사이의 순환 의존**이 드러났습니다.

기존에는 두 기능을 별도 패키지로 관리했지만 실제 도메인에서는 체크리스트가 연결된 일정을 조회해야 했고 일정 상태 변경도 체크리스트 항목 상태와 맞물려 있었습니다. 인터페이스로 의존 방향만 우회하기보다 두 개념이 독립된 기능 경계로 나뉘어 있는 것이 적절한지부터 팀원들과 다시 검토했습니다. 논의 끝에 **일정은 체크리스트 항목에 속하는 하위 개념**이라는 데 합의하고 일정의 도메인·서비스·저장소를 모두 `checklist` 패키지로 통합했습니다.

### 도입 비용(85개 파일 수정)과 PR CI 연동

팀 컨벤션을 ArchUnit 규칙으로 옮기려던 작업은 기존 위반 정리까지 맞물리며 [도입 PR #94](https://github.com/woowacourse-teams/2026-bibbidi/pull/94)에서 **총 85개 파일 변경**으로 이어졌습니다. 여기에는 규칙 13개 추가와 `appointment`·`checklist` 통합뿐 아니라 `catalog`의 `checklist` JPA Repository 참조 제거, 인증 애너테이션의 `common.auth` 이동, Controller 통합 테스트의 Repository 주입 제거 및 `@Sql` 픽스처 정리가 함께 포함됐습니다. 초기 정리 비용과 리뷰 부담이 컸으며, 규칙 추가와 기존 구조 리팩터링을 작은 PR로 나눴다면 리뷰가 훨씬 수월했을 것입니다.

작성한 `ArchitectureConventionTest`는 일반 테스트 단계에 포함해 로컬과 PR CI에서 자동 실행되도록 구성했습니다([백엔드 CI 개편 PR #499](https://github.com/woowacourse-teams/2026-bibbidi/pull/499) 이후 `dev-be`·`release-be` 대상 PR에서 `./gradlew check bootJar`로 실행).

### 결과와 한계

- **로컬 테스트와 CI에서 의존 규칙 위반 즉시 차단**: 다른 기능의 내부 구현이나 Service를 잘못 참조하는 실수를 PR을 올리기 전 로컬 테스트에서 바로 잡아내어 리뷰어가 같은 규칙을 반복 설명하던 일을 없앴습니다.
- **리뷰 초점의 변화**: 기계적인 패키지·의존 규칙 확인을 테스트에 넘긴 뒤 일반 PR에서는 Service 책임과 비즈니스 규칙에 집중했습니다(단, 리뷰 시간이나 수정 요청 횟수의 정량 감소 폭은 측정하지 않았습니다).
- **신규 기능에 맞춰 13개에서 16개 규칙으로 확장**: 2026년 11월 기준 대화(`chat`) Service와 밸런스게임(`balancegame`) Service의 Spring AI(Artificial Intelligence)·HTTP(Hypertext Transfer Protocol) 직접 의존 제한, SSE(Server-Sent Events) 연결 관리 코드의 대화 처리 Service 직접 의존 제한 규칙을 추가해 총 16개 규칙을 운영하고 있습니다.
- **도구의 한계와 검증 사각지대**:
  1. **책임 배치 판단 불가**: 규칙을 통과하더라도 특정 Service에 책임이 몰리거나 어댑터 위치가 어색한 문제는 도구가 알 수 없어 [AI 챗봇 PR #421](https://github.com/woowacourse-teams/2026-bibbidi/pull/421#discussion_r4237282779)처럼 팀원들이 직접 논의해 결정해야 합니다.
  2. **수동 관리 목록(`FEATURES`)과 예외 규칙**: 기능 간 접근 검사는 `ArchitectureConventionTest`의 `FEATURES` 문자열 목록을 기준으로 동작하므로 새 기능 패키지 추가 시 목록을 갱신해야 하며, ArchUnit 규칙 자체를 수정하는 PR은 제약이 느슨해지지 않도록 사람이 직접 검토해야 합니다.
  3. **동작 검증과의 분리**: 정적 의존 구조 검사와 별개로 테스트의 결함 검출력을 확인하기 위해 11월에는 [PIT 변이 테스트 도입 PR #795](https://github.com/woowacourse-teams/2026-bibbidi/pull/795)를 진행해 수정된 운영 클래스 3개에서 변이 31개 중 24개 감지를 확인했습니다.

### 다시 한다면: 도입 시점과 변경 단위 조정

기획과 요구사항이 수시로 바뀌는 초기 MVP 단계부터 아키텍처 규칙을 촘촘하게 강제하면 요구사항이 바뀔 때마다 코드와 규칙을 함께 고쳐야 합니다. 또한 한 PR에서 85개 파일을 한꺼번에 수정하며 겪은 리뷰 부담을 줄이도록 다시 진행한다면 다음 순서로 적용하겠습니다.

1. **MVP 구현 및 핵심 요구사항 검증** → 2. **기획 안정화 후 기능 경계 합의** → 3. **기능 단위의 작은 PR로 점진적 리팩터링** → 4. **지속할 규칙을 ArchUnit으로 자동화** → 5. **책임 배치와 비즈니스 규칙에 사람 리뷰 집중**
