### 문제

백엔드 PR을 리뷰하며 다른 기능의 내부 구현을 직접 참조하거나 기능끼리 서로 의존하는 코드를 여러 번 봤습니다. [회원 탈퇴 PR #42](https://github.com/woowacourse-teams/2026-bibbidi/pull/42#discussion_r3885559907)에서는 `UserDeletionService`가 Repository 네 개를 주입받고 체크리스트의 삭제 순서까지 알고 있었습니다. 체크리스트의 저장 구조가 바뀌면 회원 탈퇴 코드도 함께 고쳐야 하는 형태라, 삭제 책임을 해당 기능으로 돌리자고 리뷰했습니다.

[준비 항목 추가 PR #35](https://github.com/woowacourse-teams/2026-bibbidi/pull/35#discussion_r3876886468)에서는 `catalog`가 `checklist`의 JPA Repository를 참조하고 `checklist`는 `catalog`의 Service를 참조해 순환 의존이 생긴다는 지적이 나왔습니다. 당시에는 기능 구현을 진행하고 이 구조를 후속 작업으로 남겼습니다. 이런 판단을 대면과 PR 리뷰에서 계속 해야 했지만, 리뷰만으로 이후의 같은 의존이 다시 생기는지 자동으로 확인할 수는 없었습니다. [CodeRabbit도 연동돼 있었지만](https://github.com/woowacourse-teams/2026-bibbidi/pull/94#issuecomment-5580276077), 당시 저장소의 스타가 10개 미만이라 자동 리뷰가 실행되지 않았습니다.

### 선택과 작업

기존 팀 컨벤션 중 코드로 판단할 수 있는 항목을 골라 `ArchitectureConventionTest`에 **ArchUnit 규칙 13개를 직접 작성했습니다.** 계층과 기능 사이 의존 방향 4개, 클래스 이름과 위치 5개, 작성 규칙 4개입니다. 특히 기능 패키지 사이의 순환 참조와 다른 기능의 Repository를 직접 호출하는 코드를 막고자 했습니다. 한 기능을 고칠 때 다른 기능까지 손대야 하는 일을 줄이기 위해서입니다. 이름이나 애너테이션 사용 규칙도 함께 넣었지만, 이 규칙들이 책임 배치를 대신 판단해 주지는 않습니다.

[도입 PR #94](https://github.com/woowacourse-teams/2026-bibbidi/pull/94)에서는 규칙이 드러낸 기존 위반을 팀과 함께 정리했습니다. 일정과 체크리스트는 개념상 별개였지만 실제 코드에서는 밀접하게 협력해 하나의 기능 경계로 합쳤고, 기능 사이에서 필요한 값은 일정 요약 DTO로 전달했습니다. 인증 애너테이션은 공통 패키지로 옮겼습니다. 팀원은 `catalog`가 `checklist`의 JPA Repository를 직접 주입하던 코드를 제거하고 조회 API를 조정했습니다. 이 PR의 변경 파일 **85개**에는 이러한 구조 변경 외에 Controller 통합 테스트와 픽스처 정리도 포함됩니다.

도입 당시에는 `release-be` 대상 백엔드 PR의 CI가 `./gradlew test`를 실행했습니다. ArchUnit 테스트가 이 단계에 포함되어 있어 로컬에서 위반을 확인하고 고친 뒤 PR 검사를 받았습니다. 이후 [CI 개편 PR #499](https://github.com/woowacourse-teams/2026-bibbidi/pull/499)에서 `./gradlew check bootJar`로 바뀌었고, 현재 워크플로는 `dev-be`와 `release-be` 대상 PR에서 실행됩니다.

### 결과와 한계

- 도입 PR에서 기존 순환 참조를 정리하고, 작성한 구조 규칙을 테스트로 계속 실행할 수 있게 했습니다. 규칙 수는 이후 대화 서비스의 HTTP·Spring AI 타입 의존, 밸런스게임 서비스의 Spring AI 타입 의존, SSE 연결 관리의 의존을 검사하는 항목이 추가되어 현재 16개입니다.
- 코드를 작성하다 로컬 테스트에서 위반을 발견해 CI에 올리기 전에 수정한 적이 있습니다. 리뷰 시간이 얼마나 줄었는지, 변경 비용이 얼마나 감소했는지는 측정하지 않았습니다.
- [AI 챗봇 PR #421](https://github.com/woowacourse-teams/2026-bibbidi/pull/421#discussion_r4237282779)에서는 AI 도구 어댑터를 어느 패키지에 둘지 팀과 논의했습니다. 코드가 규칙을 통과해도 책임을 어디에 둘지는 사람이 판단해야 했습니다.
- 새로운 기능 패키지를 추가하면 `ArchitectureConventionTest`의 `FEATURES` 목록도 수정해야 합니다. 목록에서 빠진 기능은 다른 기능 접근 검사 대상이 아니어서 위반을 놓칠 수 있습니다. 규칙이나 예외를 고치는 변경도 테스트 통과만으로는 안전성을 확인하기 어려워 별도로 리뷰해야 합니다.
- 테스트가 코드의 동작 변화를 잡는지는 별개 문제라, 11월에는 [변경된 운영 클래스에 PIT 변이 검사를 도입](https://github.com/woowacourse-teams/2026-bibbidi/pull/795)했습니다. 과거에 변경한 클래스 세 개를 로컬에서 시험했을 때 변이 31개 중 24개를 잡았습니다. 이 수치는 ArchUnit 규칙의 성능을 뜻하지 않습니다.

### 다시 한다면

처음부터 객체지향 규칙을 촘촘하게 강제하기보다 MVP를 빠르게 개발해 실제 사용자를 먼저 모으겠습니다. 사용자 반응을 확인하면서 변경 범위가 작은 곳부터 하나씩 객체지향적으로 리팩터링하겠습니다. 이번에는 규칙을 도입하며 한 PR에서 넓은 범위를 고쳐야 했습니다. 다음에는 리팩터링을 작은 변경으로 나눠 진행하고, 팀에서 계속 지켜야 할 규칙이 분명해졌을 때 자동 검사를 추가하겠습니다.
