### 문제

- FCM(Firebase Cloud Messaging)과 SMS 공급사를 요청 안에서 동기로 부르면 공급사가 느릴 때 요청 스레드까지 묶임
- 메모리 비동기로만 넘기면 202 응답 뒤 서버가 죽을 때 아직 보내지 않은 알림이 사라짐
- 재시작이나 재시도로 같은 이벤트를 다시 처리하면 같은 알림이 두 번 만들어질 수 있음

### 원인

- 외부 공급사 호출과 DB 상태 저장은 하나의 트랜잭션으로 묶을 수 없음
- 메모리 비동기에서는 보낼 알림이 프로세스 메모리에만 있어 서버가 죽으면 남는 기록이 없음
- 이벤트를 다시 처리할 때 이미 만든 알림인지 구분할 기준이 없었음

### 고려한 방법

- **동기 호출 유지**: 구현은 단순하지만 공급사가 느리면 사용자 요청까지 느려짐
- **메모리 비동기**: 응답은 빨라지지만 서버가 죽으면 알림이 사라짐
- **RabbitMQ 같은 외부 브로커**: 재전달과 실패 격리를 브로커가 맡지만 서버를 따로 운영해야 함
- **Spring Modulith 이벤트 발행 기록과 DB 중복 방지**: 이미 쓰는 DB에 발행 기록을 남겨 재시작 후 다시 발행하고 중복은 DB 제약으로 막음

### 선택과 이유

- **Spring Modulith 이벤트 발행 기록과 DB 중복 방지를 택함.** 사용자와 처리량이 작은 단계에서 브로커를 따로 운영하는 복잡도와 서버 비용이 이득보다 크다고 판단함
- 요청 트랜잭션에는 발송 제한 차감과 이벤트 발행 기록만 커밋하고 202로 응답함. 재시작하면 끝나지 않은 이벤트를 다시 발행함
- 이벤트 ID와 발송 수단으로 만든 중복 방지 키에 유니크 제약을 걸어 알림 행을 한 번만 만듦
- 발송 직전 조건부 UPDATE로 대기나 실패 상태 알림만 처리 중으로 바꾸고 1행을 바꾼 워커만 발송함. 처리 중에 오래 머문 알림은 60초마다 도는 스케줄러가 다시 처리함

### 감수한 것

- **알림을 잃지 않는 쪽을 택함.** 공급사가 문자를 받은 직후 결과를 기록하기 전에 서버가 죽으면 같은 알림이 한 번 더 나가는 중복을 감수함
- 브로커가 주는 실패 격리와 재전달 기능은 쓰지 못하고 스케줄러와 상태 값으로 직접 다룸
- **발송 도중 장애를 가짜 공급사로 시험함.** 발송을 30초 늦춘 가짜 공급사를 써서 강제 종료 시점을 맞췄고 대신 실제 Solapi에서의 동작은 확인하지 못함

### 결과

- 알림 요청은 공급사를 기다리지 않고 202로 끝남
- 장애 시험에서 발송 도중 컨테이너를 강제 종료하자 처리 중 알림 8건이 남았고 재시작 뒤 8건 모두 발송됨
- 같은 시험에서 발송한 SMS 114건은 공급사 메시지 ID가 모두 달라 같은 알림이 두 번 나간 흔적이 없음

### 다시 한다면

- 처리량이 늘거나 서버를 여러 대 띄우는 시점에는 외부 브로커 도입을 다시 검토함
- 장애 시험을 가짜 공급사가 아니라 실제 Solapi로 해서 동작을 확인함
