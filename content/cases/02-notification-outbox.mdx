### 문제 상황: 사용자보다 메시지 브로커가 더 큰 서비스

**이번 구조 변경의 핵심은 실사용자가 적은 서비스 규모에 맞춰 과도한 RabbitMQ 서버를 걷어내면서도, Spring Modulith의 이벤트 발행 기록과 DB(Database) 기반 발송 상태 관리를 분리해 서버 장애 후에도 미완료 알림을 끝까지 복구하는 것이었습니다.**

ImHere는 사용자의 도착·이탈 사실을 다른 사용자에게 알리는 서비스입니다. 알림이 제때 전달되지 않으면 상대방이 사용자의 상태를 파악할 수 없으므로 알림 전달은 서비스의 핵심 기능입니다. 초기에는 알림 요청을 비동기로 처리하려고 RabbitMQ를 도입했습니다. API(Application Programming Interface) 서버에서 메시지를 발행하면 RabbitMQ Consumer가 이를 받아 FCM(Firebase Cloud Messaging)이나 SMS(Short Message Service) 발송을 처리하고, 실패한 메시지는 DLQ(Dead Letter Queue, 실패 메시지 보관 큐)에 보관해 운영자가 관리자 API로 재처리하는 구조였습니다. 그러나 도입 당시 별도의 성능 요구사항이나 대규모 트래픽이 있었던 것은 아니며 메시지 큐를 써보고 싶다는 기술적 관심이 출발점이었습니다.

시간이 지나 AWS(Amazon Web Services) 프리 티어 종료가 다가오면서 인프라 운영 비용을 다시 검토했습니다. 당시 서비스는 단일 애플리케이션 서버로 동작하고 있었고 알림 기능을 실제로 쓰는 사용자도 사실상 저 한 명뿐이었습니다. 이런 상황에서 브로커 전용 서버를 따로 유지하고 애플리케이션과 별개로 배포·상태 구성을 관리하는 것은 제공하는 기능에 비해 운영 비용이 지나치게 컸습니다.

결국 서비스 규모에 맞지 않는 RabbitMQ를 제거하기로 결정했습니다. 다만 인프라를 줄인다는 이유로 기존 알림의 안정성까지 포기할 수는 없었습니다. RabbitMQ를 쓰던 동안 알림 유실이나 중복 발송 문제를 겪지 않았기 때문에, 브로커를 걷어낸 뒤에도 접수된 알림이 사라지지 않고 장애 후 복구되는 구조를 직접 보장해야 했습니다.

### 요구사항: 중복 가능성보다 알림 유실 방지를 우선

RabbitMQ를 제거하면서 세운 기준은 세 가지였습니다.

1. **별도의 메시지 브로커 서버를 운영하지 않을 것**: 서비스 규모가 작은 단계에서 불필요한 인프라를 줄이는 것이 직접적인 목적이었습니다.
2. **서버 장애로 알림 요청이 유실되지 않게 할 것**: HTTP(Hypertext Transfer Protocol) 요청을 정상 접수한 뒤 실제 발송을 마치기 전에 서버가 종료되더라도 재시작 후 발송을 다시 시도해야 했습니다.
3. **기존 비동기 처리 방식을 유지할 것**: FCM이나 Solapi의 응답을 기다리느라 사용자의 HTTP 요청이 지연되지 않도록 알림 요청은 `HTTP 202 Accepted`로 즉시 접수하고 실제 발송은 별도 흐름에서 처리해야 했습니다.

이 과정에서 **최소 한 번 전달(At-least-once)**을 지향하기로 결정했습니다. ImHere는 도착·이탈 사실을 전달하는 서비스라 같은 알림을 두 번 받으면 불편하겠지만 아예 전달받지 못하면 서비스의 핵심 목적 자체가 무너집니다. 장애 상황에서 생길 수 있는 중복 발송 가능성을 일정 부분 감수하더라도 미완료 알림을 보존하고 재처리하는 방향을 택했습니다. 여기서 목표로 삼은 최소 한 번 전달은 최종 단말 도착 보장이 아니라, 애플리케이션이 접수한 알림을 보존하고 서버 장애 이후에도 외부 공급사에 발송을 다시 시도할 수 있게 만드는 것이었습니다.

### 대안 검토: 메시지 브로커 없이 전달 기록을 유지하는 방법

#### 1. RabbitMQ 유지

메시지 전달과 재처리, Consumer 기반 비동기 실행, DLQ 기반 실패 메시지 보관 기능을 그대로 쓸 수 있고 구조 변경 위험도 피할 수 있습니다. 하지만 당시 서비스 규모에서는 브로커의 높은 처리량과 확장성을 활용할 일이 없었고 별도 서버를 계속 운영해야 한다는 점이 인프라 축소 목적과 어긋났습니다.

#### 2. Transactional Outbox 패턴 직접 구현

기존 관계형 DB의 비즈니스 트랜잭션 안에서 이벤트를 Outbox 테이블에 기록하고 별도 작업자가 이를 조회해 발송하는 방식입니다. RabbitMQ 서버가 필요 없고 데이터 변경과 이벤트 기록 사이의 불일치를 줄일 수 있습니다. 그러나 이벤트 기록 테이블, 발행 상태 관리, 미완료 이벤트 조회, 재처리 및 정리 정책을 모두 직접 구현해야 했습니다. 브로커 운영 부담을 줄이려는 상황에서 이벤트 발행 인프라까지 직접 개발하고 유지보수하는 것은 과도하다고 판단했습니다.

#### 3. Spring Modulith Event Publication Registry와 DB 상태 관리 결합

Spring Modulith의 모듈 간 이벤트 처리 기능을 살피면서 이벤트 발행 기록을 DB에 저장하고 리스너의 처리 완료 여부를 추적할 수 있다는 점을 확인했습니다. 범용 메시지 브로커는 아니지만 당시 서비스에서 필요했던 이벤트 기록과 실패 후 재처리의 기반으로 쓸 수 있었고, 이미 Spring Modulith를 사용 중이라 새 인프라를 들일 필요도 없었습니다.

결국 **Spring Modulith Event Publication Registry와 기존 DB를 결합하는 방식을 선택했습니다.** 다만 Event Publication Registry가 외부 SMS나 FCM 발송 성공까지 보장하지는 않으므로, 이벤트 전달 기록과 별도로 실제 알림의 발송 상태를 저장하고 복구하도록 두 기록을 분리해 설계했습니다.

### 구현: 이벤트 전달 기록과 실제 발송 상태를 분리해 관리

#### 1. 이벤트 발행과 HTTP 202 응답 분리

기존에는 알림 요청을 RabbitMQ로 보내고 Consumer가 발송을 처리했지만 변경 후에는 Spring의 `ApplicationEventPublisher`를 감싼 `DomainEventPublisher`로 도메인 이벤트를 발행했습니다. 알림 요청을 접수하는 서비스에 `@Transactional`을 적용하고 Spring Modulith의 `@ApplicationModuleListener`가 커밋된 트랜잭션의 이벤트를 비동기로 처리하게 구성했습니다. 트랜잭션이 커밋되면 `HTTP 202 Accepted`를 즉시 반환하고 별도 흐름에서 FCM이나 SMS 발송을 시작해 외부 공급사 호출을 요청 경로에서 분리했습니다.

#### 2. Event Publication Registry를 통한 이벤트 기록과 알림 기록의 분리

서버가 이벤트를 메모리에만 둔 채 종료되면 이미 접수한 알림이 사라지므로 Spring Modulith Event Publication Registry를 사용해 이벤트 발행 기록을 DB에 남기고 리스너 완료 여부를 추적했습니다.

여기서 핵심 설계 판단은 **이벤트 발행 기록과 실제 알림 발송 기록을 분리**한 것입니다. 이벤트 기록은 특정 리스너의 이벤트 처리가 끝났는지를 다루는 반면, 알림 기록은 누구에게 어떤 내용을 보내려 했는지와 외부 공급사 호출 성공 여부 및 실패 횟수를 다룹니다. 이벤트 기록만으로 발송 전체 생애주기를 관리하지 않고 알림 도메인의 상태를 별도 테이블에 저장했습니다.

#### 3. Notification 테이블로 발송 상태 보존 및 DLQ 대체

기존 DLQ가 맡던 실패 메시지 보관과 운영자 재처리 기능을 대체하려고 [`Notification.kt`](https://github.com/ImHereOfRati/server/blob/main/src/main/kotlin/com/kdongsu5509/notifications/domain/Notification.kt) 도메인에 상태와 발송 시도 횟수, 마지막 오류를 기록했습니다. 2026년 8월 2일 최초 전환 시점의 주요 상태는 네 가지였습니다.

- `PENDING`: 발송 요청이 등록되어 발송할 수 있는 상태
- `SENT`: 발송 처리가 성공한 상태
- `FAILED`: 발송에 실패했지만 재시도할 수 있는 상태
- `DEAD`: 정해진 재시도 한도를 모두 소진한 최종 실패 상태

실패할 때마다 시도 횟수를 늘리고 최대 3회에 도달하면 `DEAD` 상태로 전환했습니다. 외부 공급사 장애가 길어질 때 같은 요청을 무한정 반복해도 성공할 가능성이 낮으므로 자동 재시도를 멈추고 운영자가 원인을 확인한 뒤 재발송 여부를 결정하게 했습니다.

#### 4. 실패 알림 관리와 운영자 재처리

새로운 구조에서는 최종 실패한 `Notification` 행 자체를 운영 단위로 삼았습니다. 관리자 API와 화면에서 실패 알림의 수신 대상, 종류, 시도 횟수, 마지막 오류를 확인하고 개별 재발송·다건 재처리·폐기를 수행할 수 있게 만들었습니다. 또한 발송 실패 시 `NotificationDeliveryFailed` 이벤트를 발행해 Discord 서버 오류 채널로 경보를 보내 외부 공급사 장애를 운영자가 즉시 인지하도록 했습니다.

#### 5. 복구 스케줄러로 미완료 알림 재처리

이벤트 리스너가 알림을 DB에 등록한 뒤 Solapi를 호출하는 도중 서버가 종료되면 알림 행은 남아 있어도 발송은 끝나지 않은 상태가 됩니다. 이를 복구하려고 [`NotificationRecoveryScheduler.kt`](https://github.com/ImHereOfRati/server/blob/main/src/main/kotlin/com/kdongsu5509/notifications/scheduler/NotificationRecoveryScheduler.kt)를 구현했습니다. 최초 전환 시점에는 기본 60초 간격으로 스케줄러를 실행해 일정 시간 이상 `PENDING`이나 `FAILED` 상태로 남아 있는 알림을 최대 100건씩 조회해 다시 발송했습니다. **Spring Modulith는 이벤트 리스너 완료 여부를 추적하고, 복구 스케줄러는 DB에 남은 실제 발송 작업의 완료 여부를 확인**하도록 두 복구 책임을 명확히 나눴습니다.

#### 6. 동일 이벤트의 중복 알림 등록 방지

최소 한 번 전달을 지향하면 같은 이벤트가 다시 전달될 때 알림 행이 여러 개 생길 수 있습니다. 이를 막으려고 최초 전환 시점부터 이벤트 ID(Identifier)와 발송 수단을 조합한 중복 방지 키를 사용했습니다.

```text
dedupeKey = "{eventId}:{notificationMethod}"
```

이 키에 DB `UNIQUE` 제약을 걸어 이미 처리 중이거나 등록된 동일 이벤트가 다시 전달되더라도 알림 행이 중복 생성되지 않게 차단했습니다. 다만 알림 행 중복 생성을 막는 것과 외부 공급사의 중복 발송을 막는 것은 다릅니다. Solapi가 요청을 접수한 직후 서버가 결과를 DB에 기록하기 전에 종료되면 복구 과정에서 같은 SMS를 다시 보낼 여지가 남지만, 알림이 완전히 사라지는 것보다 중복 수신의 피해가 작다고 판단해 이를 감수했습니다.

### 이후 안정성 개선: 발송 중 장애와 동시 실행 제어

2026년 8월 2일의 [최초 RabbitMQ 제거 작업](https://github.com/ImHereOfRati/server/commit/e9f0f76b6b0b48c7c22cca3610349127c6676fad)과 이후 안정성 보강 작업은 구분됩니다. 최초 전환에는 이벤트 기록, DB 중복 방지 키, 알림 상태 관리, 관리자 재발송, `PENDING`·`FAILED` 복구 스케줄러가 포함됐으나 조건부 `UPDATE` 기반 선점 기능은 없었습니다.

이후 [`NotificationDeliveryFacade.kt`](https://github.com/ImHereOfRati/server/blob/main/src/main/kotlin/com/kdongsu5509/notifications/application/service/NotificationDeliveryFacade.kt)를 개선하면서 발송 중인 작업을 뜻하는 `PROCESSING` 상태를 추가하고 DB의 조건부 `UPDATE`로 발송 작업을 선점하게 바꿨습니다. 발송 가능한 알림을 `PROCESSING`으로 바꾸는 데 성공한 실행 흐름만 실제 공급사를 호출하게 해 여러 실행 흐름이 같은 알림을 동시에 처리할 때 생기는 중복 발송을 줄였습니다. 또한 `PROCESSING` 상태에서 서버가 종료된 경우에도 일정 시간이 지나면 복구 대상이 되도록 보강했고, 공급사 발송 결과를 단정하기 어려운 상황은 `UNKNOWN` 상태로 분리해 공급사 메시지 ID로 실제 결과를 조회하도록 다듬었습니다(사례 3 참고).

### 장애 시험: 서버 강제 종료 후 미완료 알림 복구 검증

단위 테스트로 상태 전이와 재시도 메서드를 검증하더라도 외부 공급사 응답을 기다리는 도중 프로세스가 갑자기 종료됐을 때 미완료 알림이 실제로 복구되는지는 별도로 확인해야 했습니다. 이를 직접 입증하기 위해 2026년 9월 4일 서버 강제 종료 장애 시험을 수행했습니다.

#### 1. 시험 환경과 절차

AWS 서울 리전에 별도 부하 테스트 환경을 꾸리고 실제 Solapi 대신 응답 시간을 30초 지연시킨 가짜 SMS 공급사(`LoadTestExternalMessageAdapter`)를 연결했습니다. 실제 SMS를 대량 발송하지 않고도 공급사 응답 지연 중 장애와 복구 기록을 확인하기 위해서였습니다.

1. 가짜 SMS 공급사의 응답 지연을 30초로 설정했습니다.
2. k6로 `POST /api/notifications` 요청을 발생시켰습니다.
3. 발송 처리 도중 `docker kill`로 애플리케이션 컨테이너를 강제 종료했습니다.
4. MySQL에서 미완료 알림의 상태와 공급사 메시지 ID를 확인했습니다.
5. 컨테이너를 수동으로 재시작한 뒤 복구 스케줄러가 실행된 이후의 최종 상태를 확인했습니다.

#### 2. 시험 결과와 확인한 사항

컨테이너 강제 종료 직후 MySQL을 확인하자 ID `20003`부터 `20010`까지 SMS 알림 **8건이 `PROCESSING` 상태**로 남아 있었고 공급사 메시지 ID는 모두 `NULL`이었습니다. 컨테이너를 재시작한 뒤 복구 스케줄러가 돌자 **미완료 상태로 멈췄던 8건 모두 `SENT` 상태로 전환**되었고 각 알림에 가짜 공급사가 발급한 메시지 ID가 기록되었습니다. 시험 전체에서는 `SENT` 상태의 SMS 알림 114건과 서로 다른 공급사 메시지 ID 114개를 확인했습니다.

시험 과정에서는 복구 시점에 대한 예상과 실제 코드 설정의 차이도 확인했습니다. `PENDING`과 `FAILED` 알림은 5분 기준으로 복구 대상을 조회했지만 `PROCESSING` 상태 알림은 10분 이상 정체되었을 때 복구하도록 구현되어 있어, 스케줄러가 60초마다 돌더라도 중단 직후 60초 안에 즉시 복구되는 것은 아니었습니다. 또한 `docker kill` 이후 컨테이너 자동 재기동을 시험한 것이 아니라 수동 재시작 이후 애플리케이션의 미완료 알림 복구 동작을 검증한 결과입니다.

### 결과와 감수한 한계

- **별도 브로커 서버 제거 및 비동기 응답 유지**: RabbitMQ Consumer, DLQ 관리 API, 브로커 설정을 모두 걷어내 운영 대상을 줄이면서 `HTTP 202 Accepted` 기반 비동기 처리 구조를 유지했습니다.
- **강제 종료 장애 후 미완료 알림 8건 전량 복구**: 발송 도중 컨테이너를 종료해 `PROCESSING` 상태로 멈춘 SMS 알림 8건이 재시작 후 모두 `SENT`로 복구되는 것을 입증했습니다.
- **정량 비교의 한계와 DB 부하 감수**: RabbitMQ 제거 전후의 실제 월간 인프라 절감액이나 DB CPU(Central Processing Unit) 사용률, 쿼리 부하, 지연 시간은 측정하지 못했습니다. 이벤트 기록과 알림 상태 저장 및 주기적 복구 조회를 DB가 맡게 되어 알림량이 급증하면 DB 쓰기·조회 부하가 커지지만 당시 사용량이 적어 이를 감수했습니다.
- **외부 발송과의 트랜잭션 경계 및 가짜 공급사 검증**: 공급사 발송과 DB 상태 기록을 한 트랜잭션으로 묶을 수 없어 공급사 접수 직후 서버가 죽으면 중복 발송될 가능성이 남아 있으며, 장애 시험은 30초 지연 가짜 공급사로 진행해 실제 Solapi 장애 상황까지 모두 검증한 결과는 아닙니다.

### 다시 한다면

**이번 작업은 단순히 RabbitMQ를 Spring Modulith로 교체한 것이 아니라, 서비스 규모에 맞지 않는 인프라를 걷어내면서도 반드시 지켜야 할 알림 복구 가능성을 정의하고 실제 장애 시험으로 입증한 경험입니다.** 현재와 같은 소규모 서비스를 다시 설계하더라도 기술적 관심만으로 브로커를 도입하기보다 Spring Modulith와 기존 DB를 활용하는 방식을 택하겠습니다.

다만 기술 선택의 효과를 비용과 성능 수치로 충분히 남기지 못한 점은 아쉬웠습니다. 다시 진행한다면 전환 전후의 월간 인프라 비용과 DB CPU 사용률, 쿼리 처리량, 알림 처리 지연 시간을 먼저 측정하고, 여러 알림 발생량을 가정한 부하 시험으로 현재 DB 기반 구조가 어느 규모까지 버티는지 확인해 외부 메시지 브로커를 다시 도입할 정량 기준선을 세우겠습니다.
