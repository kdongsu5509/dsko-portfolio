### 문제

알림 요청을 RabbitMQ로 처리하고 있었는데 브로커 서버를 따로 운영하는 비용이 부담이었습니다. 사용자와 처리량이 작은 단계라 이득보다 비용이 크다고 보고 RabbitMQ를 걷어내기로 했습니다. 다만 RabbitMQ를 쓰는 동안 알림 유실이나 중복은 없었으므로, 걷어낸 뒤에도 같은 수준을 지켜야 했습니다.

### 원인

RabbitMQ를 빼면 보낼 알림을 보관하고 다시 전달하는 일을 서버가 직접 맡아야 합니다. 보낼 알림이 프로세스 메모리에만 있으면 202 응답 뒤 서버가 죽을 때 남는 기록이 없어 알림이 사라질 수 있습니다. 게다가 재시작이나 재시도 때 같은 이벤트를 다시 처리하게 되므로, 이미 만든 알림인지 구분할 기준이 없으면 같은 알림이 두 번 만들어질 수 있습니다.

### 고려한 방법

- **RabbitMQ 유지**: 재전달과 실패 격리를 브로커가 맡아 지금까지 문제가 없었지만 브로커 서버 비용이 계속 듭니다.
- **outbox 패턴 직접 구현**: 추가 비용 없이 발행 기록을 DB에 남길 수 있지만, 기록 테이블과 재발행 로직을 직접 만들고 관리해야 합니다.
- **Spring Modulith 이벤트 발행 기록과 DB 중복 방지**: 이미 쓰는 DB에 발행 기록을 남겨 재시작 후 다시 발행하고, 중복은 DB 제약으로 막습니다.

### 선택과 이유

**Spring Modulith 이벤트 발행 기록과 DB 중복 방지를 택했습니다.** 사용자와 처리량이 작은 단계에서 브로커를 따로 운영하는 서버 비용이 이득보다 크다고 판단했고, 이미 쓰는 DB로 브로커가 하던 재전달과 중복 방지를 대신할 수 있었습니다. 그래서 요청 트랜잭션에는 발송 제한 차감과 이벤트 발행 기록만 커밋하고 202로 응답하며, 재시작하면 끝나지 않은 이벤트를 다시 발행합니다. 같은 이벤트가 다시 처리돼도 알림이 중복되지 않도록 이벤트 ID와 발송 수단으로 만든 중복 방지 키에 유니크 제약을 걸어 알림 행을 한 번만 만듭니다.

발송 직전에는 조건부 UPDATE로 대기나 실패 상태 알림만 처리 중으로 바꾸고, 1행을 바꾼 워커만 발송합니다. 처리 중에 오래 머문 알림은 60초마다 도는 스케줄러가 다시 처리합니다.

### 감수한 것

- **알림을 잃지 않는 쪽을 택했습니다.** 공급사가 문자를 받은 직후 결과를 기록하기 전에 서버가 죽으면 같은 알림이 한 번 더 나가는 중복을 감수합니다.
- RabbitMQ가 주던 실패 격리와 재전달 기능은 쓰지 못하고 스케줄러와 상태 값으로 직접 다룹니다.
- **발송 도중 장애를 가짜 공급사로 시험했습니다.** 발송을 30초 늦춘 가짜 공급사를 써서 강제 종료 시점을 맞췄고, 대신 실제 Solapi에서의 동작은 확인하지 못했습니다.

### 결과

- 브로커 서버를 따로 운영하지 않아도 되고, 알림 요청은 공급사를 기다리지 않고 202로 끝납니다.
- 장애 시험에서 발송 도중 컨테이너를 강제 종료하자 처리 중 알림 8건이 남았고, 재시작 뒤 8건 모두 발송되었습니다.
- 같은 시험에서 발송한 SMS 114건은 공급사 메시지 ID가 모두 달라 같은 알림이 두 번 나간 흔적이 없습니다.

### 다시 한다면

- 처리량이 늘거나 서버를 여러 대 띄우는 시점에는 외부 브로커 도입을 다시 검토합니다.
- 장애 시험을 가짜 공급사가 아니라 실제 Solapi로 해서 동작을 확인합니다.
