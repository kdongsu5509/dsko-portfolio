## 문제

- FCM과 SMS 같은 외부 공급사 호출을 요청 안에서 동기로 처리하면 공급사가 느릴 때 요청 스레드까지 함께 묶이는 구조였음
- 그렇다고 메모리 비동기로만 넘기면 202를 응답한 뒤 서버가 죽을 때 아직 보내지 않은 알림이 흔적 없이 사라질 수 있었음
- 재시작이나 재시도로 같은 이벤트가 다시 처리되면 같은 알림이 두 번 만들어지고 두 번 나갈 수 있었음

## 해결

- 요청 트랜잭션에는 발송 제한 차감과 Spring Modulith의 이벤트 발행 기록만 함께 커밋하고 202로 응답했음. 재시작하면 완료되지 않은 이벤트를 다시 발행하도록 설정
- 리스너는 이벤트 ID와 발송 수단으로 만든 중복 방지 키에 유니크 제약을 걸어 같은 이벤트로 알림 행이 두 번 생기지 않게 했고 이미 있으면 실패 상태일 때만 다시 시도
- 발송 직전에는 대기나 실패 상태인 알림만 처리 중으로 바꾸는 조건부 UPDATE를 실행해 1행을 바꾼 워커만 발송하게 했고 60초마다 도는 스케줄러가 오래 멈춘 알림을 다시 처리

## 결과

- 알림 요청은 공급사 응답을 기다리지 않고 202로 끝남
- 장애 시험에서 발송 지연 30초를 걸고 처리 도중 앱 컨테이너를 강제 종료하자 처리 중 알림 8건이 남았고 재시작 뒤 8건 모두 발송 완료로 바뀌었음
- 같은 시험에서 발송된 SMS 114건의 공급사 메시지 ID가 모두 달라 같은 알림이 두 번 나간 흔적은 없었음

## 한계

- 멈춘 처리 중 알림을 대기로 되돌려 다시 보내는 방식이라 공급사가 문자를 받은 직후 결과를 기록하기 전에 서버가 죽으면 한 번 더 나갈 수 있음. 잃지 않는 쪽을 택한 대신 이 경로의 중복은 막지 못함
- 대기와 실패는 5분, 처리 중은 10분이 지나야 복구 대상이 되어 재시작 직후 바로 복구되지는 않음
- 장애 시험은 실제 Solapi가 아니라 가짜 공급사로 진행했음
