## 문제

- FCM과 SMS 공급사를 요청 안에서 동기로 부르면 공급사가 느릴 때 요청 스레드까지 묶임
- 메모리 비동기로만 넘기면 202 응답 뒤 서버가 죽을 때 아직 보내지 않은 알림이 사라짐
- 재시작이나 재시도로 같은 이벤트를 다시 처리하면 같은 알림이 두 번 만들어질 수 있음

## 해결

- 요청 트랜잭션에는 발송 제한 차감과 Spring Modulith 이벤트 발행 기록만 커밋하고 202로 응답함. 재시작하면 끝나지 않은 이벤트를 다시 발행함
- 이벤트 ID와 발송 수단으로 만든 중복 방지 키에 유니크 제약을 걸어 알림 행을 한 번만 만듦
- 발송 직전 조건부 UPDATE로 대기나 실패 상태 알림만 처리 중으로 바꾸고 1행을 바꾼 워커만 발송함. 오래 멈춘 알림은 60초마다 도는 스케줄러가 다시 처리함

## 결과

- 알림 요청은 공급사를 기다리지 않고 202로 끝남
- 장애 시험에서 발송 도중 컨테이너를 강제 종료하자 처리 중 알림 8건이 남았고 재시작 뒤 8건 모두 발송됨
- 같은 시험에서 나간 SMS 문자 114건의 공급사 메시지 ID가 모두 달라 같은 알림이 두 번 나간 흔적이 없음

## 한계

- 공급사가 문자를 받은 직후 결과를 기록하기 전에 서버가 죽으면 같은 알림을 한 번 더 보낼 수 있음. 잃지 않는 쪽을 택해 이 경로의 중복은 남겨 둠
- 처리 중 알림은 10분이 지나야 복구 대상이 되어 재시작 직후 바로 복구되지 않음
- 장애 시험은 실제 Solapi 대신 발송을 30초 늦춘 가짜 공급사로 진행함
