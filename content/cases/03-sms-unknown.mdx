- **문제**: 일반적인 SMS(Short Message Service) 발송 시험 중 동일한 문자가 3분 간격으로 두 번 도착했습니다. 앞서 [사례 2](/cases/notification-outbox)에서 서버 중단 시 알림 유실을 막기 위해 실패 건 자동 재시도를 도입했는데, Solapi가 이미 접수했을 가능성이 있는 불확실한 예외까지 `FAILED`로 기록해 복구 스케줄러가 같은 문자를 다시 발송하고 있었습니다.
- **본인 행동**: 공식 문서만으로 알기 어려운 Solapi SDK(Software Development Kit) 1.1.0 소스 코드를 직접 분석해 확실한 미접수(`FAILED`)와 접수 여부 불확실(`UNKNOWN`)을 분리하고, `UNKNOWN`은 자동 재발송에서 제외한 뒤 공급사 메시지 ID(Identifier)가 있을 때만 60초마다 실제 결과를 조회하도록 변경했습니다.
- **결과와 검증 범위**: 결과 불명 건을 자동 재발송 대상에서 제외하는 흐름을 단위 테스트(`SolapiAdapterTest`)와 정상 발송 5회 시험(중복 0건)으로 확인했습니다. 단, **공급사가 요청을 접수한 직후 응답이 끊기는 핵심 장애 상황은 아직 모의 시험으로 재현하지 못했으므로**, 모든 중복 발송의 완전한 방지가 아니라 **결과 불명 건의 무조건적인 자동 재발송 경로를 차단한 것**이 입증된 성과 범위입니다.

### 문제 발견: 알림 유실 방지 정책이 부른 3분 간격 중복 SMS

ImHere는 사용자의 출발·도착 사실을 SMS로 전달합니다. SMS는 외부 공급사인 Solapi를 호출해 발송하므로 요청 건수마다 실제 비용이 발생합니다. 2026년 8월 일반적인 SMS 발송 기능을 확인하던 중 같은 문자가 3분 간격으로 두 번 도착하는 현상을 발견했습니다.

직전에 Solapi 오류 처리 로직을 추가했기 때문에 해당 변경을 가장 먼저 의심했습니다. 발송 로직을 점검한 뒤 Solapi의 응답 전체를 로깅하도록 수정해 실제 응답과 내부 처리 흐름을 대조했습니다.

당시 알림 시스템은 [RabbitMQ를 제거하며 구축한 DB 기반 복구 구조(사례 2)](/cases/notification-outbox) 위에서 동작하고 있었습니다. 브로커 제거 시점에는 서버 장애로 알림이 사라지는 일을 막기 위해 미완료·실패 작업을 복구 스케줄러가 다시 발송하도록 설계했지만, 건당 요금이 부과되는 외부 SMS 연동에서 공급사가 이미 접수했을 가능성이 있는 예외까지 `FAILED`로 기록하자 복구 스케줄러가 동일한 SMS를 재발송하는 부작용이 나타났습니다. 이에 **알림 유실 방지 일변도였던 초기 재시도 정책을 수정해, 접수 여부를 확신할 수 없는 요청은 자동 재발송을 멈추는 방향으로 위험 선택 기준을 바꿨습니다.**

### 원인 분석: 예외 발생과 요청 미접수는 같은 뜻이 아니었습니다

#### 1. 공식 문서만으로는 예외의 의미를 구분하기 어려웠습니다

처음에는 공식 Solapi SDK 문서를 확인했지만 문서 설명만으로는 발송 API(Application Programming Interface)에서 던지는 예외가 정확히 어떤 상황을 뜻하는지 판단하기 어려웠습니다. 특히 재시도 여부를 결정하려면 다음 두 상황을 엄격히 구분해야 했습니다.

- **Solapi가 발송 요청을 접수하지 않았다는 사실이 확인된 경우**: 재시도해도 중복 발송이 발생하지 않습니다.
- **애플리케이션이 응답을 받지 못해 Solapi의 접수 여부를 모르는 경우**: 이미 접수된 요청일 수 있으므로 곧바로 재발송하면 중복 문자가 나갑니다.

기존 오류 처리는 이 차이를 반영하지 않고 모든 예외를 동일하게 실패로 취급했습니다. 문서의 설명만으로 추측해 결론을 내리는 대신 실제 사용 중이던 Solapi SDK 1.1.0의 소스 코드를 열어 어떤 조건에서 각 예외가 발생하는지 직접 확인했습니다.

#### 2. Solapi SDK 1.1.0 소스 코드에서 확인한 예외 발생 조건

SDK의 `DefaultMessageService.send()`는 내부적으로 [`MessageServiceHelper.kt`](https://github.com/solapi/solapi-kotlin/blob/v1.1.0/src/main/java/com/solapi/sdk/message/lib/MessageServiceHelper.kt)의 `processSendRequest()`를 호출합니다. 이 함수의 구현을 분석한 결과 HTTP(Hypertext Transfer Protocol) 성공 응답 안에서도 메시지 접수 결과에 따라 예외가 나뉘고 HTTP 비성공 응답은 별도 예외로 처리되고 있었습니다.

```kotlin
if (failedMessageList.isNotEmpty() &&
    (count.total ?: 0) == failedMessageList.count()
) {
    throw SolapiMessageNotReceivedException(
        "메시지 발송 접수에 실패했습니다."
    )
}
```

위 코드는 응답에 포함된 모든 메시지가 접수에 실패했을 때만 `SolapiMessageNotReceivedException`을 던집니다. 반면 HTTP 성공 응답의 본문이 비어 있으면 `SolapiEmptyResponseException`을 던지고 HTTP 비성공 응답이면 `SolapiUnknownException`을 던집니다. 나아가 네트워크 타임아웃처럼 HTTP 호출 도중 발생하는 예외는 발송 요청이 공급사에 실제로 접수됐는지 알려주지 않습니다. 결국 예외가 발생했다는 사실만으로 SMS를 다시 발송해도 안전하다고 단정할 수 없었습니다.

### 해결 방향 검토

중복 발송을 막기 위해 당시 검토한 선택지는 네 가지였습니다.

| 대안 | 장점 | 한계 |
| --- | --- | --- |
| 기존 실패 처리와 재시도 유지 | 알림 유실 가능성을 낮춤 | 이미 접수된 SMS를 다시 발송할 수 있음 |
| 서버가 지정한 식별자로 결과 조회 | 기존 요청과 바로 연결 가능 | 사용하려던 Solapi 메시지 조회 방식에서는 해당 값을 조회 키로 쓰기 어려움 |
| 발송 전에 메시지 그룹 생성 | 응답이 끊기더라도 그룹 ID(Identifier)를 미리 확보 가능 | 발송 흐름을 추가 API 호출이 필요한 2단계 구조로 바꿔야 함 |
| `UNKNOWN` 상태 분리 | 기존 발송 구조를 유지하면서 중복 발송 위험을 즉시 제거 | 메시지 ID를 받기 전에 응답이 끊기면 결과 조회 불가 |

당시에는 실제 발생하고 있던 중복 발송 문제를 빠르게 차단하는 일이 가장 시급했습니다. 발송 전에 메시지 그룹을 생성하도록 전체 발송 흐름을 뜯어고치기보다, **기존 발송 구조를 유지하면서 발송 결과가 불확실한 상태를 `UNKNOWN`으로 분리하고 확인 가능한 경우에만 공급사 조회 API로 결과를 확정하는 방식을 선택했습니다.**

### 구현: 확실한 실패(`FAILED`)와 결과 불명(`UNKNOWN`)을 분리

변경의 핵심은 예외가 발생했을 때 무조건 `FAILED`로 저장하던 흐름을 고쳐 재시도 가능 여부를 `FAILED`와 `UNKNOWN` 두 상태로 분리한 것입니다.

#### 1. 접수 실패가 확실한 예외만 재시도 대상으로 분류

[`SolapiAdapter.kt`](https://github.com/ImHereOfRati/server/blob/main/src/main/kotlin/com/kdongsu5509/notifications/adapter/out/solapi/SolapiAdapter.kt)에서 잘못된 요청, 인증 오류, 미접수처럼 공급사가 요청을 처리하지 않았다고 확신할 수 있는 예외만 `fail`로 분류했습니다. 반대로 접수 여부를 단정할 수 없는 그 밖의 예외는 `unknown`으로 분리했습니다.

```kotlin
return if (
    e is SolapiBadRequestException ||
    e is SolapiInvalidApiKeyException ||
    e is SolapiMessageNotReceivedException
) {
    MessageSendResult.fail(errorMessage)
} else {
    MessageSendResult.unknown(errorMessage)
}
```

이 분기를 적용해 결과 불명 건은 일반 실패 건과 달리 자동 재발송 대상에서 즉시 제외했습니다.

#### 2. 결과 불명 건은 60초마다 공급사 메시지 ID로 상태 조회

`UNKNOWN` 상태라도 Solapi가 발급한 메시지 ID가 남아 있다면 실제 발송 결과를 사후에 확인할 수 있습니다. [`NotificationRecoveryScheduler.kt`](https://github.com/ImHereOfRati/server/blob/main/src/main/kotlin/com/kdongsu5509/notifications/scheduler/NotificationRecoveryScheduler.kt)가 60초마다 결과 불명 건을 조회하고 공급사 메시지 ID로 Solapi의 메시지 조회 API를 호출하도록 구현했습니다. 조회 결과에 따라 상태를 `SENT` 또는 `FAILED`로 확정하며 아직 발송 중이거나 결과를 확정할 수 없으면 `UNKNOWN` 상태를 유지합니다. 반면 공급사 메시지 ID를 응답받기 전에 통신이 끊긴 경우에는 이 방식으로 조회할 수 없었습니다.

#### 3. 재시도 한도(최대 2회)와 운영자 Discord 경보

확실한 실패(`FAILED`)로 분류된 SMS가 반복 실패하더라도 공급사를 무한정 호출하지 않도록 재시도 한도를 걸었습니다. 동일 알림의 공급사 발송 호출을 최대 2회로 제한하고 한도에 도달하면 추가 발송 요청 없이 `DEAD` 상태로 전환한 뒤 Discord 채널로 운영자에게 경보를 보냅니다. 공급사 장애가 길어질 때 자동 재시도가 불필요한 호출 비용을 계속 발생시키는 일을 막기 위한 장치입니다.

### 감수한 한계

결과 불명 건의 자동 재발송을 멈추면서 실제로 발송되지 않은 SMS가 누락될 가능성은 의도적으로 감수했습니다. 예를 들어 다음 흐름이 발생할 수 있습니다.

1. 애플리케이션이 Solapi에 발송 요청을 보냅니다.
2. 응답을 받기 전에 네트워크 통신이 끊깁니다.
3. 애플리케이션 DB(Database)에는 공급사 메시지 ID가 남지 않습니다.
4. 발송 여부를 조회할 키가 없어 `UNKNOWN` 상태를 유지합니다.
5. 중복 발송을 막기 위해 자동으로 다시 발송하지 않습니다.

이 상황에서 Solapi가 처음부터 요청을 접수하지 못했다면 해당 SMS는 누락됩니다. 그러나 이미 접수된 요청을 다시 보내면 중복 SMS 수신과 추가 발송 비용이 곧바로 발생합니다. 실제로 중복 발송을 겪은 직후였기 때문에 불확실한 상황에서 무조건 다시 보내는 위험을 먼저 제거하기로 판단했습니다.

외부 공급사의 실제 발송과 내부 DB 상태 변경을 한 트랜잭션으로 묶을 수 없다는 구조적 한계도 남아 있습니다. 따라서 이번 개선은 정확히 한 번 발송(Exactly-once)을 보장하는 것이 아니라, **불확실한 결과에 대한 무조건적인 재시도를 걷어내 중복 발송 위험을 통제한 설계**입니다.

### 검증 결과와 남은 과제

[`SolapiAdapterTest.kt`](https://github.com/ImHereOfRati/server/blob/main/src/test/kotlin/com/kdongsu5509/notifications/adapter/out/solapi/SolapiAdapterTest.kt)와 `NotificationDeliveryFacadeTest` 단위 테스트로 공급사 응답 및 예외 분류, 중복 등록 방지, 재시도 흐름을 검증했고, 실제 Solapi 연동 환경에서 정상 발송 요청을 **총 5회** 실행해 각 요청마다 SMS가 한 번씩 수신되는 것을 확인했습니다.

다만 이 검증 결과가 입증하는 범위와 아직 해결해야 할 과제는 명확히 구분됩니다.

- **입증한 범위**: 예외 유형에 따라 `FAILED`와 `UNKNOWN`을 분리해 결과 불명 건을 자동 재발송 대상에서 제외하는 코드 경로를 구현했고, 정상 발송 5회에서 기존 기능이 문제없이 동작함을 확인했습니다.
- **미검증 범위 (핵심 장애 상황 미재현)**: 정상 발송 5회 시험은 **공급사가 요청을 접수한 뒤 응답이 끊기는 핵심 장애 상황**에서의 중복 발송 방지를 입증하지 못합니다.
- **우선 해결할 코드·테스트 과제**: 현재 [`SolapiAdapter.kt`](https://github.com/ImHereOfRati/server/blob/main/src/main/kotlin/com/kdongsu5509/notifications/adapter/out/solapi/SolapiAdapter.kt)에는 응답 상태 코드 `2000`이 성공과 `UNKNOWN` 양쪽 상태 코드 집합에 중복 포함되어 조건문 순서상 성공으로 먼저 처리되는 문제가 남아 있습니다. 상태 코드 집합 간 중복을 제거하는 코드 수정과 단위 테스트 보강이 최우선 과제입니다.

### 다시 한다면

- **상태 코드 `2000` 중복 분류 수정 및 WireMock 장애 재현 테스트 추가**: 우선 상태 코드 집합에서 `2000` 중복을 제거한 뒤, WireMock으로 공급사가 요청을 접수한 직후 타임아웃이 발생하는 상황을 재현해 `UNKNOWN` 저장 여부와 복구 스케줄러의 재발송 차단 여부, 메시지 ID 보유 시 상태 확정 흐름을 자동화 테스트로 검증하겠습니다.
- **발송 요청 전에 조회 가능한 그룹 식별자를 먼저 확보하겠습니다**: 이번에는 발송 응답에 담긴 메시지 ID로 결과 불명 건을 조회하다 보니 응답 자체가 끊기면 결과를 확인할 방법이 없었습니다. 다시 설계한다면 발송 전에 메시지 그룹을 먼저 생성해 그룹 ID를 확보해 두고, 발송 응답이 유실되더라도 미리 확보한 그룹 ID로 공급사 처리 결과를 끝까지 조회하도록 개선하겠습니다.

### 회고

**외부 시스템과 연동할 때는 공식 문서의 설명만으로 실제 동작을 단정하지 않고 SDK 소스 코드와 실제 응답 로그로 예외의 정확한 의미를 확인해야 한다는 원칙을 세웠습니다.** 처음에는 Solapi SDK 문서와 기본 인터페이스에 의존해 모든 예외를 실패로 다루었지만, 실제 중복 발송을 겪은 뒤 응답 전체를 로깅하고 SDK 1.1.0의 [`MessageServiceHelper.kt`](https://github.com/solapi/solapi-kotlin/blob/v1.1.0/src/main/java/com/solapi/sdk/message/lib/MessageServiceHelper.kt) 구현을 직접 열어서야 예외마다 요청 접수 여부가 다르다는 사실을 파악했습니다.

특히 **외부 API 호출에서 예외가 발생했다는 사실과 외부 시스템이 요청을 처리하지 않았다는 사실은 전혀 다릅니다.** 이 차이를 구분하지 않은 재시도는 장애를 복구하기보다 중복 과금과 중복 발송이라는 새로운 장애를 만듭니다. 앞으로도 외부 API 동작이 모호할 때는 추측에 기대지 않고 실제 응답과 SDK 구현 코드로 근거를 확보해 상태 전이 정책을 설계하겠습니다.
