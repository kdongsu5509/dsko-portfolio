### 문제

객체지향을 다시 공부하며 코드 전반을 고치기 시작했지만, 한 도메인을 손보면 다른 도메인까지 고쳐야 했고 도메인 사이에 순환 의존이 생겼습니다. AI 에이전트에게 수정을 맡겨도 같은 문제가 반복되었습니다.

### 원인

기존 코드는 DB 테이블과 JPA 엔티티를 중심으로 짜여 있어서, 다른 도메인의 정보가 필요하면 그 도메인의 내부 클래스나 엔티티를 직접 참조했습니다. 이런 참조를 막는 규칙이 없었기 때문에 AI 에이전트는 기존 코드를 읽고 같은 참조를 더 만들었습니다. 게다가 이벤트로 연결한 부분은 의존 방향이 코드에 드러나지 않아, 어떤 도메인이 어떤 도메인에 기대는지 파악하기 어려웠습니다.

### 고려한 방법

- **코드를 직접 수정**: 빌드 구조는 그대로 두지만, 같은 참조가 다시 생겨도 자동으로 잡아낼 방법이 없습니다.
- **Gradle 멀티 프로젝트로 분리**: 도메인별로 프로젝트를 나눠 빌드 의존성을 명시할 수 있지만, 기존 코드와 빌드 설정을 옮기는 범위가 큽니다.
- **Spring Modulith 도입**: 빌드 프로젝트를 나누지 않고 모듈 경계를 정의해 내부 타입 참조와 순환 의존을 검사합니다. 다만 기존 위반을 정리해야 검사를 통과합니다.

### 선택과 이유

**Spring Modulith를 택했습니다.** 빌드 구조를 그대로 둔 채 내부 타입 참조와 순환 의존을 검사할 수 있어 겪던 문제와 맞았고, 당시 주목받던 기술인 데다 마침 [Spring Camp 2026](https://springcamp.ksug.org/2026/ko/)에서 이 라이브러리가 나온 배경을 들은 것도 계기가 되었습니다. 직접 수정은 참조를 하나씩 찾느라 오래 걸리고, 놓친 참조가 남거나 이후 변경에서 같은 문제가 다시 생길 수 있었습니다. Gradle 멀티 프로젝트는 의존 관계를 검증하려고 프로젝트 구조까지 바꾸기에는 범위가 너무 컸습니다.

검사를 바로 강제하면 모든 빌드가 깨지므로 검사 테스트는 잠시 끄고 남은 위반 목록을 테스트 코드에 적어 두었습니다. 그다음 여러 모듈이 함께 쓰는 타입을 공개 인터페이스로 옮기며 커밋을 나눠 위반을 줄였고, 인증 사용자 정보 하나만 옮겨도 84건이 사라졌습니다. 이벤트 뒤에 숨은 의존은 명시적인 호출로 바꿔 의존 방향이 생성자에 드러나게 했습니다. 위반을 모두 지운 뒤에는 경계 검사를 켜고 main 배포 워크플로의 테스트 단계에 넣었습니다.

### 감수한 것

**학습 비용을 감수했습니다.** Spring Modulith의 모듈 경계와 공개 인터페이스, 검사 규칙을 익히는 데 시간이 들었습니다. 대신 경계를 한 번 정의해 두면 AI 에이전트가 같은 참조나 순환 의존을 다시 만들어도 배포 전에 잡을 수 있어, 매번 직접 확인하다 놓치는 위험을 줄이는 쪽이 낫다고 판단했습니다.

### 결과

- 공개하지 않은 내부 타입 참조 224건과 순환 의존 7건을 모두 0건으로 줄였습니다.
- 이후 main에 들어온 경계 위반 2건을 배포 전에 막았습니다. 그중 하나는 탈퇴 API에 인증 모듈 애너테이션을 붙여 생긴 인증과 회원 사이 순환이었고, 애너테이션을 공용 모듈로 옮겨 끊었습니다.
- 정리하는 동안 기존 테스트 686개는 모두 통과했습니다.

### 다시 한다면

- 도메인 사이 의존 방향과 순환 의존, 다른 도메인의 Repository 직접 호출을 막는 규칙을 Spring Modulith 대신 ArchUnit으로 작성합니다. 처음 규칙을 만드는 데 시간이 더 들더라도 기능을 추가할 때마다 공개 인터페이스 설정을 맞추는 부담이 줄고, 필요한 경계만 검사할 수 있습니다.
- 경계 검사를 PR 검사나 커밋 전 단계로 앞당깁니다. 혼자 개발하며 main에 바로 올린 변경은 PR 검사를 거치지 않아 위반을 배포 단계에서야 발견했습니다.
