### 문제

- 한 곳을 고치면 다른 도메인까지 깨지는데 어디까지 번지는지 코드만으로는 알 수 없음
- AI 에이전트에게 기능을 맡길수록 이런 일이 잦아짐

### 원인

- AI 에이전트가 다른 모듈의 내부 클래스와 JPA 엔티티를 직접 참조하는 코드를 계속 만듦
- 모듈 경계가 코드로 강제되지 않아 컴파일만 되면 어느 모듈의 내부든 가져다 쓸 수 있었음. 이벤트로 연결된 부분은 의존이 이벤트 뒤에 숨어 방향조차 보이지 않음
- Spring Modulith 경계 검사를 켜자 공개하지 않은 타입 참조 224건과 순환 의존 7건이 나옴

### 고려한 방법

Spring Modulith 문서가 기존 프로젝트를 모듈 구조로 옮길 때 권하는 방식 중에서 위반 종류에 맞는 것을 골랐음

- **열린 모듈로 선언**: 다른 모듈이 내부 타입까지 쓸 수 있게 풀어 줌. 빠르게 위반을 없애지만 그만큼 경계 검사가 느슨해짐
- **공개 인터페이스로 필요한 타입만 공개**: 다른 모듈이 꼭 알아야 하는 패키지만 골라 내놓고 나머지는 계속 숨김
- **공개 API 계약으로 교체**: 다른 모듈의 내부 서비스를 직접 부르던 코드를 그 모듈이 내놓은 계약 인터페이스 호출로 바꿈

검사를 켜는 시점도 정해야 했음. 바로 강제하면 위반 224건 때문에 모든 빌드가 깨짐

### 선택과 이유

- **열린 모듈은 모두가 함께 쓰는 shared, support와 관리자 기능에만 씀.** 문서에서도 기존 프로젝트를 옮기는 동안 쓰라고 한 장치라 도메인 모듈에 쓰면 경계를 둔 의미가 사라진다고 봄
- **도메인 모듈은 공개 인터페이스와 API 계약으로 풂.** 인증 사용자 정보 하나를 공개 인터페이스로 옮기자 84건이 사라졌고 회원과 친구 모듈은 api 패키지의 계약만 내놓게 함
- 이벤트 뒤에 숨은 의존은 명시적인 계약 호출로 바꿔 의존 방향이 생성자에 드러나게 함
- **경계 검사를 일단 끄고 위반 목록부터 기록함.** 남은 위반을 테스트 코드에 적어 두고 커밋마다 줄어드는 것을 확인하며 정리했고 마지막 2건을 지운 뒤 검사를 켬
- **검사를 PR이 아닌 main 배포 워크플로의 테스트 단계에 넣음.** 혼자 개발하며 main에 바로 올리는 변경은 PR 검사를 거치지 않으므로 배포 직전이 모든 변경이 지나가는 유일한 길목이었음

### 감수한 것

- 정리가 끝나는 시점까지 새 위반을 막지 못하는 기간을 감수함
- 열린 모듈로 둔 shared, support, 관리자 기능은 내부가 모두 열려 있어 그 안의 경계는 검사가 지켜 주지 못함
- 위반이 배포 단계에서야 걸림. 실제로 main에 바로 올린 변경 때문에 배포가 멈춘 뒤에야 순환을 발견한 적이 있음
- 경계 검사는 모듈 사이 참조만 봄. 모듈 안에서 책임을 어디에 둘지는 여전히 사람이 판단함

### 결과

- 공개하지 않은 타입 참조 224건과 순환 의존 7건을 모두 0건으로 줄임
- 이후 main에 들어온 경계 위반 2건을 배포 전에 막음. 그중 하나는 탈퇴 API에 인증 모듈 애너테이션을 붙여 생긴 인증과 회원 사이 순환이었음. 애너테이션을 공용 모듈로 옮겨 순환을 끊음
- 정리하는 동안 기존 테스트 686개는 모두 통과함

### 다시 한다면

- 경계 검사를 PR 검사나 커밋 전 단계로 앞당겨 main에 바로 올려도 위반이 배포까지 가지 않게 함
