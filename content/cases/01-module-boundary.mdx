### 문제

**이 리팩터링의 핵심 목표는 개발자가 도메인의 책임과 협력 계약을 직접 정의하고, AI(Artificial Intelligence) 에이전트가 작성한 코드라도 모듈 경계를 침범하면 배포 전에 자동으로 차단하는 구조를 만드는 것이었습니다.** 객체지향 학습을 바탕으로 기존 프로젝트를 고치기 시작했을 때, Service에 집중된 비즈니스 로직과 도메인 간 결합 때문에 코드를 안전하게 변경하기 어렵다는 문제를 마주했습니다.

우아한테크코스에서 객체지향을 학습한 뒤 기존 코드를 다시 살펴보니 DB(Database) 테이블 구조를 중심으로 작성되어 있었습니다. 도메인 객체는 데이터를 보관하는 역할에 머물렀고, 친구 요청을 수락할 수 있는지 같은 비즈니스 규칙은 모두 Service에 모여 있었습니다. 기능 하나를 이해하려면 Service가 호출하는 여러 Repository와 다른 도메인 코드까지 따라가며 읽어야 했습니다.

기존 동작을 보호하려고 테스트를 먼저 작성하려 했지만 무엇을 테스트해야 하는지조차 분명하지 않았습니다. 작은 규칙 하나를 검증하려고 해도 여러 Repository와 외부 도메인 객체를 함께 다루는 Service의 협력 구조를 전부 준비해야 했습니다. 게다가 다른 도메인의 JPA(Java Persistence API) 엔티티와 Repository를 직접 참조하는 코드가 여러 곳에 퍼져 있어, 한 도메인의 변경이 다른 도메인의 수정으로 번졌습니다.

당시 AI 에이전트를 활용해 코드를 수정하고 있었기 때문에, 도메인 경계 규칙이 코드로 정의되어 있지 않으면 AI가 기존 코드의 잘못된 참조를 그대로 따라 하거나 새로운 의존을 만들어도 일관되게 잡아낼 수 없었습니다. 결국 기존 코드를 일회성으로 정리하는 데 그치지 않고, **도메인의 책임을 명확히 정의한 뒤 그 경계가 이후 변경에서도 유지되도록 자동 검증할 장치**가 필요했습니다.

### 원인

#### 1. DB 테이블을 중심으로 도메인을 설계했습니다

기존 도메인 모델은 비즈니스 개념과 규칙보다 DB에 저장되는 데이터를 표현하는 데 집중되어 있었습니다. 도메인 객체는 자신의 상태를 직접 판단하거나 바꾸지 못했고, Service가 데이터를 조회한 뒤 비즈니스 규칙을 판단하고 상태를 변경하는 일까지 맡았습니다.

그 결과 Service에는 비즈니스 규칙 판단, Repository 데이터 조회·저장, 타 도메인 협력이라는 서로 다른 성격의 책임이 한데 섞였습니다. 친구 요청이 이미 처리된 상태에서 다시 수락할 수 없는지 확인하려 해도 규칙 자체보다 Service의 협력 구조까지 함께 준비해야 했습니다. 단순히 Service 코드가 긴 수준을 넘어 **비즈니스 규칙을 책임질 객체가 뚜렷하지 않아 변경과 테스트의 단위를 나눌 수 없는 구조**였습니다.

#### 2. 데이터의 소유권과 기능의 책임을 구분하지 않았습니다

대표적인 사례는 사용자 검색 기능이었습니다. 기존 `user` 모듈의 `SpringQueryDSLUserRepository`는 사용자 정보를 검색하면서 `friends` 모듈의 `QFriendRelationJpaEntity`를 직접 참조했습니다. 검색 결과에서 이미 친구 관계가 있는 사용자를 제외하려고 사용자 Repository가 친구 관계 테이블까지 직접 조회한 것입니다. 반대로 `friends` 모듈도 친구 관계를 처리하기 위해 `user` 모듈 정보를 참조하면서 두 모듈 사이에 양방향 의존이 생겼습니다.

이 구조는 `user` 모듈에 정의한 '사용자 정보를 관리하고 대표한다'는 책임을 위반했습니다. 사용자 정보를 검색하는 일은 `user`의 책임이지만 친구를 찾는 과정에서 기존 친구 관계를 제외할지 판단하는 일은 `friends`의 책임입니다. 기존 코드는 사용자 데이터가 저장된 곳을 중심으로 기능을 구현하면서 친구 관계 판단까지 사용자 Repository에 넣었고, **데이터가 저장된 위치를 기준으로 기능을 배치한 탓에 도메인의 책임과 실제 코드의 책임이 어긋났습니다.**

#### 3. 도메인 경계를 검증하는 규칙이 없었습니다

기능별로 패키지를 나누어 코드를 관리했지만 패키지가 나뉘어 있다는 사실만으로 내부 구현은 보호되지 않았습니다. 다른 도메인의 JPA 엔티티나 Repository를 직접 참조해도 컴파일은 정상 통과했고, 순환 의존 역시 일반적인 기능 테스트만으로는 걸러지지 않았습니다.

개발자가 도메인의 책임을 정리하더라도 이후 추가되는 코드가 같은 원칙을 따르는지 매번 눈으로 확인해야 했습니다. 특히 AI 에이전트가 Service와 Repository를 수정하는 환경에서는 AI가 설계 의도를 알아서 지켜주길 기대하기보다, 지켜야 할 규칙을 코드로 명시하고 위반 여부를 결정적인 테스트로 확인할 필요가 있었습니다.

### 고려한 방법

#### 1. 코드를 직접 수정하고 리뷰로 확인하는 방법

다른 도메인의 내부 타입 참조를 직접 찾아 걷어내고 코드 리뷰로 재발을 막는 방법입니다. 별도 라이브러리를 도입하거나 빌드 구조를 바꾸지 않아도 되지만, 수정해야 할 참조가 여러 곳에 반복되어 있었고 당장 위반을 해결해도 이후 변경에서 같은 문제가 재발하는 것을 막을 수 없었습니다. 무엇보다 AI 에이전트가 수정한 코드를 매번 사람 눈으로만 확인해서는 의존 관계를 빠짐없이 검증할 수 없었습니다.

#### 2. Gradle 멀티 프로젝트로 분리하는 방법

도메인별로 Gradle 프로젝트를 분리하면 프로젝트 간 의존 관계를 빌드 설정으로 명시해 컴파일 단계에서 잘못된 참조를 막을 수 있습니다. 하지만 당시 프로젝트는 단일 Gradle 프로젝트 안에 기능별 패키지로 구성되어 있었습니다. 기존 기능을 유지하면서 도메인 모델을 재설계하는 일이 우선이었기 때문에 모듈 경계를 검증하려고 소스 코드 위치와 빌드 설정까지 바꾸는 것은 당장 필요한 해결 범위를 넘어섰습니다.

#### 3. Spring Modulith를 도입하는 방법

[Spring Camp 2026](https://springcamp.ksug.org/2026/ko/)에서 Spring Modulith가 등장한 배경을 접하며 이 라이브러리를 알게 됐습니다. Spring Modulith는 단일 Spring Boot 프로젝트 안에서도 애플리케이션 모듈을 정의하고 모듈의 비공개 내부 타입 참조와 순환 의존을 테스트로 검사합니다.

기존 Gradle 프로젝트 구조를 그대로 유지하면서 겪고 있던 문제를 바로 확인할 수 있었기에 **Spring Modulith를 먼저 빠르게 적용해 실제 위반을 확인하며 리팩터링을 진행하기로 결정했습니다.** 당시에는 Spring Modulith가 내부적으로 ArchUnit을 활용한다는 점이나 ArchUnit으로 직접 규칙을 작성하는 선택지를 깊이 알지 못했으나, 이후 라이브러리를 학습하면서 두 접근 방식의 차이를 분명히 이해하게 됐습니다.

### 선택과 해결 과정

#### 1. Spring Modulith를 먼저 도입해 내부 참조 위반 224건과 순환 의존 7건을 확인했습니다

도메인 모델을 모두 재설계한 뒤에 검증 도구를 붙이는 대신 리팩터링 초기부터 Spring Modulith를 도입했습니다. `ApplicationModules.verify()`로 프로젝트의 모듈 경계를 검사한 결과 **공개되지 않은 내부 타입 참조 위반 224건과 순환 의존 7건**이 드러났습니다.

이 수치가 서로 다른 설계 문제 224개를 뜻하지는 않았습니다. 일부 잘못된 의존 관계가 여러 클래스에서 반복되면서 다수의 위반으로 집계된 결과였습니다. 그래서 위반을 하나씩 기계적으로 지우기보다 반복되는 참조의 공통 원인을 찾고 해당 타입의 책임과 공개 범위를 다시 정의하는 방식으로 접근했습니다.

검사를 즉시 필수 단계로 켜면 기존 위반 때문에 테스트가 실패하므로 `ApplicationModules.verify()` 테스트는 잠시 비활성화했습니다. 대신 남아 있는 위반과 순환 의존을 테스트 코드에 기록해 해결 대상을 관리하면서 도메인별로 책임을 재정의하고 커밋 단위로 위반을 줄여 나갔습니다.

#### 2. 도메인의 책임을 직접 정의하고 비즈니스 규칙을 도메인 객체로 옮겼습니다

위반을 해결할 때 가장 핵심이었던 작업은 코드를 옮기는 일이 아니라 **어떤 도메인이 해당 책임을 가져야 하는지 결정하는 일**이었습니다. Spring Modulith는 어느 모듈이 다른 모듈의 내부 타입을 참조하는지 알려줄 뿐 그 기능을 어느 도메인이 맡아야 하는지는 정해주지 않기 때문입니다.

각 도메인의 책임을 먼저 정의하고 실제 코드가 그 책임에 맞는지 대조했습니다. 비즈니스 규칙과 상태 변경을 어디서 처리할지는 개발자가 직접 판단해야 하므로 Domain 객체는 직접 설계하고 작성했습니다. 반면 정의한 도메인 모델에 맞춰 Service와 Repository를 고치는 작업은 AI 에이전트에 위임했습니다. AI에게 도메인의 책임과 협력 계약을 먼저 전달한 뒤 그 설계에 맞게 주변 계층을 수정하도록 맡긴 것입니다.

대표적인 사례가 [`FriendRelation.kt`](https://github.com/ImHereOfRati/server/blob/main/src/main/kotlin/com/kdongsu5509/friends/domain/FriendRelation.kt)입니다. 기존에는 Service에 비즈니스 규칙이 몰려 있었지만 재설계 이후에는 `FriendRelation`이 자신의 상태를 확인하고 허용된 상태 변경을 직접 수행합니다.

```kotlin
fun accept(
    lowNickname: String,
    highNickname: String
): FriendRelation {
    validateIsRequested()

    return replaced(
        status = FriendRelationStatus.ACCEPTED,
        message = null,
        lowAlias = FriendAlias(highNickname),
        highAlias = FriendAlias(lowNickname),
        expiresAt = PERMANENT
    )
}
```

친구 요청을 수락할 때 Service가 상태를 검사하고 필드를 직접 바꾸는 대신 `FriendRelation`이 자신의 상태가 `REQUESTED`인지 검증한 뒤 수락된 상태의 객체를 반환합니다. 이미 처리된 요청이면 예외를 던지고, 수락 전 별칭 변경이나 관계 당사자가 아닌 사용자의 별칭 변경·차단 요청도 도메인 내부에서 거부합니다. 반면 기존 친구 관계가 DB에 존재하는지 확인하는 일은 Repository 조회가 필요하므로 Service에 남겼습니다. **객체 자신의 상태만으로 판단할 수 있는 규칙은 Domain이 책임지고 데이터 조회·저장과 객체 간 협력은 Service가 조정하도록 역할을 명확히 나눴습니다.**

#### 3. 데이터 위치가 아니라 기능 책임을 기준으로 협력 관계를 다시 설계했습니다

도메인 간 결합을 끊기 위해 다른 도메인의 내부 객체를 직접 보유하거나 참조하는 대신 필요한 식별자만 갖고 공개 인터페이스로 협력하도록 변경했습니다. `friends`와 `user`의 관계가 대표적인 사례입니다.

기존 사용자 검색 Repository는 `QFriendRelationJpaEntity`를 직접 참조해 이미 친구인 사용자를 검색 결과에서 제외했습니다. 하지만 친구 후보를 추리는 일은 `friends`의 책임이고 사용자 정보를 조건에 맞게 조회하는 일은 `user`의 책임이므로, [친구 검색 책임 분리 커밋](https://github.com/ImHereOfRati/server/commit/e9f0f76b6b0b48c7c22cca3610349127c6676fad)에서 검색 흐름을 `friends`의 `FriendCandidateSearchService`로 옮겼습니다.

```kotlin
class FriendCandidateSearchService(
    private val friendRelationQueryRepository:
        FriendRelationQueryRepository,
    private val userLookupContract:
        UserLookupContract,
) {
    fun search(
        requesterId: UUID,
        keyword: String,
        pageable: Pageable
    ): Slice<UserResult> {
        val excluded =
            friendRelationQueryRepository
                .findRelatedUserIds(requesterId) + requesterId

        return userLookupContract
            .searchActiveByKeyword(keyword, excluded, pageable)
    }
}
```

변경 이후에는 `friends`가 기존 친구 관계를 조회해 검색에서 제외할 사용자 ID(Identifier) 목록을 계산하고 `user`의 공개 계약인 `UserLookupContract`를 호출해 나머지 활성 사용자를 검색합니다. `user`의 Repository에서는 친구 관계 JPA 엔티티 참조와 관계 조회 로직을 모두 걷어내어 `user`가 `friends`의 영속성 구현을 알아야 했던 의존을 끊었습니다. **사용자 데이터는 `user`가 소유하지만 친구를 검색하는 기능은 `friends`가 책임진다**는 기준을 세워 데이터를 가진 모듈이 그 데이터를 쓰는 모든 기능까지 떠안지 않게 했습니다.

#### 4. 여러 모듈에서 쓰는 타입도 책임이 있는 모듈이 소유하도록 했습니다

224건의 내부 타입 참조 위반을 해결할 때는 가장 많은 곳에서 반복 참조하던 타입부터 살폈습니다. 대표적인 대상이 인증 사용자 정보를 표현하는 `ImHereUserDetails`였습니다. 기능별 패키지 구조에서는 여러 모듈의 Controller가 인증 사용자 정보를 참조해야 하는데, 이 타입이 `auth` 모듈의 비공개 내부 패키지에 있어 다른 모듈이 참조할 때마다 경계 위반이 발생했습니다.

여러 모듈에서 쓴다는 이유로 공용 모듈로 옮길 수도 있었지만 `ImHereUserDetails`는 인증 사용자 정보를 담는 타입이므로 책임은 여전히 `auth`에 있습니다. 소유권을 옮기지 않고 `auth.security.shared`에 배치한 뒤 `@NamedInterface`로 외부 모듈에 공개하자 [모듈 경계 리팩터링 커밋](https://github.com/ImHereOfRati/server/commit/ad39b9c1373d57a32ad1e00b3ebd34e18837dc8f) 하나로 내부 타입 참조 위반 84건이 즉시 해소됐습니다. **여러 도메인에서 공통으로 사용한다는 사실과 공용 모듈이 소유해야 한다는 판단을 구분**해 책임이 있는 모듈이 소유권을 유지하되 협력에 필요한 계약만 공개했습니다.

#### 5. 이벤트로 숨겨진 협력을 명시적인 계약 호출로 변경했습니다

도메인 간 협력을 검토하면서 이벤트 뒤에 숨어 있던 불필요한 결합도 정리했습니다. 기존에는 `agreement` 모듈에서 필수 약관 동의가 끝나면 `RequiredAgreementsSatisfied` 이벤트를 발행해 사용자 활성화를 처리했습니다.

하지만 필수 약관 동의와 사용자 활성화는 한 트랜잭션으로 묶여야 하는 단일 비즈니스 흐름이었습니다. 약관 동의는 끝났는데 사용자 활성화가 실패하면 두 상태가 어긋나기 때문입니다. 동기 이벤트로 같은 트랜잭션에 묶을 수도 있었지만 이 협력에 별도 이벤트를 둘 이유가 없었고, 오히려 이벤트를 발행하는 쪽의 생성자에 사용자 활성화 의존성이 드러나지 않아 리스너까지 찾아봐야 협력을 이해할 수 있었습니다.

```kotlin
class AgreementService(
    private val userActivationContract:
        UserActivationContract,
    private val agreementRepository:
        AgreementRepository,
    private val termCatalog:
        TermCatalog,
) {
    // ...

    if (requiredSatisfied) {
        userActivationContract.activateIfPending(userId)
    }
}
```

[같은 리팩터링 커밋](https://github.com/ImHereOfRati/server/commit/ad39b9c1373d57a32ad1e00b3ebd34e18837dc8f)에서 이벤트 발행을 걷어내고 `AgreementService`가 `UserActivationContract`를 직접 주입받아 호출하도록 바꿨습니다. 비동기 분리나 다중 구독이 필요하지 않고 한 트랜잭션으로 묶여야 하는 협력은 생성자에 의존 방향이 명시적으로 드러나는 직접 호출을 택했습니다.

#### 6. 도메인의 책임에 맞춰 테스트를 재구성했습니다

도메인 모델과 협력 구조를 바꾸면서 기존 테스트도 새로 작성하거나 수정했습니다. 처음 목표는 테스트를 먼저 작성하고 코드를 고치는 것이었으나, 기존 코드에서는 무엇을 테스트해야 할지 경계가 모호해 도메인 객체를 먼저 재설계한 뒤 그 책임을 검증하는 테스트를 작성했습니다. 처음부터 TDD(Test-Driven Development, 테스트 주도 개발)로 진행하지는 못했지만 무엇을 테스트해야 하는지 분명해져 이후 TDD를 적용할 수 있는 구조를 만들었습니다.

대표적으로 [`FriendRelationTest.kt`](https://github.com/ImHereOfRati/server/blob/main/src/test/kotlin/com/kdongsu5509/friends/domain/FriendRelationTest.kt)에서는 Service나 Repository 없이 도메인 객체만으로 상태 전이 규칙을 검증합니다.

```kotlin
@Test
@DisplayName("이미 처리된 요청은 다시 수락할 수 없다")
fun cannot_accept_twice() {
    val accepted = requestedByAlice()
        .acceptWithNicknames()

    val exception = assertThrows<ImHereBaseException> {
        accepted.acceptWithNicknames()
    }

    assertThat(exception.errorCode)
        .isEqualTo(
            FriendException.FRIEND_REQUEST_ALREADY_HANDLED
        )
}
```

이미 수락된 친구 요청을 다시 수락할 수 없다는 규칙 하나를 검증할 때 DB나 Repository, Service의 협력 관계를 준비할 필요가 없어졌습니다. 반면 Service 테스트는 기존 친구 관계 조회, Repository와의 협력, 저장, 이벤트 발행 흐름을 검증하도록 나눴습니다. 테스트 코드 양이나 Mock 개수가 줄어든 수치를 따로 측정하지는 않았으나 **Domain 테스트는 객체 자신의 비즈니스 규칙을, Service 테스트는 조회·저장과 도메인 간 협력을 검증하도록 각 테스트의 책임이 명확해졌습니다.**

#### 7. 위반 224건과 순환 의존 7건을 모두 제거한 뒤 자동 검증을 활성화했습니다

내부 타입 참조 위반을 줄이는 동안 단순히 검사를 통과하려고 공개 범위를 넓히지 않았습니다. 다른 모듈이 실제로 써야 하는 타입인지, 현재 도메인의 책임을 침범하는지, 식별자나 공개 인터페이스만으로 협력할 수 있는지를 먼저 따졌습니다. 최종적으로 내부 타입 참조 위반 224건과 순환 의존 7건을 모두 0건으로 만든 뒤 일시적으로 꺼 두었던 `ApplicationModules.verify()` 검사를 켜고 main 배포 워크플로의 테스트 단계에 포함했습니다.

### 자동 검증의 실제 효과: 사람이 검수하고도 놓친 순환 의존 차단

자동 검증을 배포 파이프라인에 넣은 뒤 **AI 에이전트가 수정하고 제가 직접 검수까지 마친 코드에서 아키텍처 위반 2건을 배포 전에 실제로 잡아냈습니다.** 혼자 개발하는 프로젝트라 별도 PR(Pull Request) 승인 절차 없이 AI 에이전트에게 변경을 맡기고 로컬에서 결과를 직접 검수한 뒤 main에 Push했는데, 직접 검수한 코드에서도 의존성 위반을 놓쳤습니다.

대표적으로 회원 탈퇴 API(Application Programming Interface)에 `AllowPendingUser` 애너테이션을 적용할 때 문제가 생겼습니다. 해당 애너테이션은 `auth` 모듈에 있었는데 `user` 모듈의 Controller가 이를 참조했고, 동시에 `auth`는 사용자 정보 처리를 위해 `user`에 의존하고 있어 `auth → user → auth` 순환 의존이 만들어졌습니다. 일반적인 기능 테스트와 육안 검수에서는 놓쳤지만 Spring Modulith 경계 검사에서 실패하면서 배포 전에 문제를 발견했습니다.

이 문제는 [AllowPendingUser 위치 변경 커밋](https://github.com/ImHereOfRati/server/commit/6932e1233fdb63734245906f7ca393d10f3185b3)에서 해당 애너테이션을 공용 모듈로 옮겨 해결했습니다. 앞서 `ImHereUserDetails`를 `auth` 모듈에 남긴 결정과 달리, `AllowPendingUser`는 사용자 모듈에서도 써야 하는 공통 접근 제어 표시였고 `auth`에 남겨 두면 불필요한 역방향 의존이 생겼기 때문입니다. 사람이 AI 코드를 매번 검수하더라도 모든 의존성 문제를 눈으로 잡아낼 수는 없으며, 명시적으로 정의한 경계 규칙은 자동 검사로 일관되게 확인해야 한다는 사실을 입증한 사례였습니다.

### 감수한 것과 한계

- **Spring Modulith 학습과 초기 정리 비용**: 모듈 경계를 정의하는 방식과 `@NamedInterface` 공개 설정, 검증 규칙을 익히는 데 시간이 들었고 기존 위반 224건을 분석해 책임을 재배치하는 비용을 감수했습니다.
- **자동 검증이 좋은 객체지향 설계 자체를 보장하지는 않음**: 예를 들어 Service에 비즈니스 로직을 모두 몰아넣더라도 모듈 경계만 침범하지 않으면 검사는 통과합니다. 도메인이 어떤 책임을 가질지와 비즈니스 규칙을 어느 객체에 둘지는 여전히 개발자가 판단해야 하며, 자동 검증은 개발자가 정의한 설계 제약이 이후 변경에서도 유지되는지 확인하는 수단입니다.

### 결과

- **내부 타입 참조 위반 224건과 순환 의존 7건 모두 0건으로 해소**: `ImHereUserDetails` 공개 범위 조정으로 84건을 줄이고 `friends`와 `user`의 검색 책임을 분리하는 등 공통 원인을 해결해 모든 위반을 제거했습니다.
- **배포 전 아키텍처 위반 2건 차단**: 경계 검사 활성화 이후 탈퇴 API의 `auth → user → auth` 순환 의존을 비롯해 육안 검수에서 놓친 경계 위반 2건을 배포 전에 막았습니다.
- **도메인과 테스트의 책임 분리 및 686개 테스트 통과**: 비즈니스 규칙을 도메인 객체로 옮기고 기존 테스트를 재구성해 전체 686개 테스트 통과를 확인했으며, 도메인 단독 테스트가 가능해져 TDD를 적용할 수 있는 구조가 됐습니다.
- **AI 에이전트 활용 방식 정립**: AI에게 바로 구현을 맡기고 검수하던 방식에서 벗어나, **개발자가 도메인 책임과 협력 계약을 먼저 정의해 Domain 객체를 작성하고 AI에게 Service·Repository 변경을 위임한 뒤 자동 검사로 검증하는 흐름**을 정착시켰습니다.

### 다시 한다면

- **검증 도구 적용보다 도메인의 책임과 경계를 먼저 정의하겠습니다**: 이번에는 Spring Modulith를 먼저 돌려 발견된 위반을 쫓아가며 책임을 정리하다 보니 위반마다 책임을 어디에 둘지 매번 고민해야 했습니다. 다시 한다면 각 도메인이 맡을 비즈니스 개념과 공개 인터페이스를 먼저 정의한 뒤 코드를 재설계하고 검증 규칙을 적용해 시행착오를 줄이겠습니다.
- **Spring Modulith 대신 ArchUnit으로 필요한 규칙만 직접 정의하겠습니다**: 이 프로젝트에서 계속 검증할 규칙은 다른 도메인의 JPA 엔티티·Repository 직접 참조 금지, 도메인 간 순환 의존 금지, Controller·Service·Repository 간 의존 방향 준수 세 가지로 명확했습니다. 이후 Spring Modulith가 내부적으로 ArchUnit을 사용한다는 점을 학습한 만큼, 다시 한다면 ArchUnit으로 이 규칙들을 한 테스트 클래스에 직접 작성해 프로젝트 설계 원칙을 코드로 관리하겠습니다.
- **로컬 AI 에이전트 Hook과 CI(Continuous Integration)에서 이중으로 검증하겠습니다**: 배포 워크플로에서야 순환 의존을 발견해 다시 수정해야 했던 경험을 줄이도록, 로컬 AI 에이전트 Hook에서 아키텍처 검사를 먼저 실행해 AI가 위반을 즉시 수정하게 하고 Push 이후 CI에서 한 번 더 검증해 배포 전 차단망을 유지하겠습니다.

### 배운 점

**좋은 설계를 만드는 일과 그 설계가 유지되도록 만드는 일은 서로 다른 문제입니다.** 도메인의 책임을 한 번 정리하더라도 이후 변경에서 같은 결합이 다시 생길 수 있고, 특히 AI 에이전트에게 구현 상당 부분을 위임하는 환경에서는 AI의 비결정적인 코드 생성 결과를 사람이 매번 눈으로만 검수할 수 없습니다. **개발자가 도메인의 책임을 정의하고, AI가 구현을 돕고, 검증 가능한 설계 제약을 결정적인 아키텍처 테스트로 확인하는 개발 방식**을 정립해 일회성 리팩터링에 그치지 않고 설계 원칙을 계속 지킬 수 있는 환경을 만들었습니다.
