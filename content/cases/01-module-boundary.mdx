- **문제**: DB(Database) 테이블 중심으로 작성된 코드에서 비즈니스 규칙이 Service에 몰리고 다른 도메인의 JPA(Java Persistence API) 엔티티·Repository를 직접 참조해(내부 참조 위반 224건, 순환 의존 7건), 변경 영향 범위를 예측하거나 단위 테스트를 작성하기 어려웠습니다.
- **본인 행동 (`책임 재설계 → 경계 검사`)**: 각 도메인의 책임과 공개 계약(`@NamedInterface`)을 직접 정의해 상태 전이 규칙을 Domain 객체로 옮기고, 주변 Service·Repository 수정은 AI(Artificial Intelligence) 에이전트에 위임한 뒤 `ApplicationModules.verify()`로 모듈 경계를 자동 검증했습니다.
- **결과 (`실제 배포 전 차단`)**: 내부 참조 위반 224건과 순환 의존 7건을 모두 0건으로 해소했고, 이후 AI가 작성하고 제가 직접 눈으로 검수한 코드에서 발생한 `auth ↔ user` 순환 의존 등 아키텍처 위반 2건을 배포 전에 차단했습니다.

### 문제와 원인

우아한테크코스에서 객체지향을 학습한 뒤 기존 프로젝트를 다시 살펴보니, 도메인 객체는 데이터를 보관하는 역할에 머물러 있었고 친구 요청 수락 가능 여부 같은 비즈니스 규칙은 모두 Service에 모여 있었습니다. 작은 규칙 하나를 테스트하려고 해도 여러 Repository와 외부 도메인 객체를 함께 다루는 Service의 협력 구조를 전부 준비해야 했습니다.

구체적인 원인은 세 가지였습니다.

1. **DB 테이블 중심 설계**: 도메인 객체가 자신의 상태를 직접 판단하거나 바꾸지 못하고 Service가 데이터 조회·저장, 비즈니스 규칙 판단, 타 도메인 협력을 한꺼번에 맡았습니다.
2. **데이터 소유권과 기능 책임의 혼재**: 기존 `user` 모듈의 `SpringQueryDSLUserRepository`는 사용자 검색 결과에서 이미 친구인 대상을 제외하려고 `friends` 모듈의 `QFriendRelationJpaEntity`를 직접 참조했습니다. 사용자 데이터가 저장된 위치를 기준으로 기능을 배치한 탓에 `user`와 `friends` 사이에 양방향 결합이 생겼습니다.
3. **도메인 경계를 검증하는 규칙 부재**: 패키지만 나뉘어 있을 뿐 다른 도메인의 JPA 엔티티나 Repository를 직접 참조해도 컴파일은 정상 통과했습니다. 특히 AI 에이전트를 활용해 주변 계층을 수정하는 환경에서는 기존 코드의 잘못된 참조 방식을 AI가 그대로 재생산해도 일관되게 걸러낼 장치가 없었습니다.

### 대안 검토와 Spring Modulith 선택

- **직접 수정 후 코드 리뷰로 확인**: 별도 도구가 필요 없지만, 반복되는 내부 참조를 사람 눈으로만 확인해서는 이후 AI가 만든 코드에서 같은 결합이 재발하는 것을 막을 수 없었습니다.
- **Gradle 멀티 프로젝트 분리**: 컴파일 단계에서 의존성을 강제할 수 있으나, 기존 기능을 유지하며 도메인 모델을 재설계하는 단계에서 소스 트리와 빌드 구조까지 바꾸는 것은 당장 필요한 범위를 넘어섰습니다.
- **Spring Modulith 도입 (선택)**: [Spring Camp 2026](https://springcamp.ksug.org/2026/ko/)에서 접한 Spring Modulith는 단일 Gradle 프로젝트 구조를 유지하면서도 모듈의 비공개 내부 타입 참조와 순환 의존을 테스트(`ApplicationModules.verify()`)로 즉시 검사할 수 있어 선택했습니다.

### 해결 과정: 책임 재설계와 경계 위반 224건 해소

#### 1. 내부 참조 위반 224건과 순환 의존 7건 식별

리팩터링 초기부터 `ApplicationModules.verify()`를 실행해 **공개되지 않은 내부 타입 참조 위반 224건과 순환 의존 7건**을 확인했습니다. 이 수치는 서로 다른 설계 문제 224개를 뜻하지 않고, 일부 잘못된 의존이 여러 클래스에서 반복 참조되며 집계된 결과였습니다. 따라서 위반을 기계적으로 하나씩 지우는 대신 반복 참조되는 타입의 책임과 공개 범위를 먼저 재정의했습니다. 기존 위반을 줄이는 동안에는 검증 테스트를 잠시 비활성화하고 남은 위반 목록을 테스트에 기록해 커밋 단위로 소거해 나갔습니다.

#### 2. 비즈니스 규칙을 도메인 객체로 이동

Spring Modulith는 잘못된 참조 위치만 알려줄 뿐 기능을 어느 도메인이 맡아야 하는지는 정해주지 않습니다. 따라서 비즈니스 규칙과 상태 변경을 다루는 Domain 객체는 제가 직접 설계·작성하고, 그 설계에 맞춰 Service와 Repository를 수정하는 작업만 AI 에이전트에 위임했습니다.

대표적인 사례가 [`FriendRelation.kt`](https://github.com/ImHereOfRati/server/blob/main/src/main/kotlin/com/kdongsu5509/friends/domain/FriendRelation.kt)입니다. Service가 상태를 검사하고 필드를 바꾸던 구조에서 벗어나 `FriendRelation`이 자신의 상태를 검증하고 허용된 상태 전이를 직접 수행합니다.

```kotlin
fun accept(
    lowNickname: String,
    highNickname: String
): FriendRelation {
    validateIsRequested()

    return replaced(
        status = FriendRelationStatus.ACCEPTED,
        message = null,
        lowAlias = FriendAlias(highNickname),
        highAlias = FriendAlias(lowNickname),
        expiresAt = PERMANENT
    )
}
```

이미 처리된 요청의 재수락, 수락 전 별칭 변경, 관계 당사자가 아닌 사용자의 요청은 도메인 객체 내부에서 즉시 거부합니다. 반면 기존 친구 관계가 DB에 존재하는지 확인하는 작업은 Repository 조회가 필요하므로 Service에 남겼습니다.

이에 맞춰 테스트 책임도 분리했습니다. [`FriendRelationTest.kt`](https://github.com/ImHereOfRati/server/blob/main/src/test/kotlin/com/kdongsu5509/friends/domain/FriendRelationTest.kt)에서는 DB나 Repository, Service 없이 도메인 객체만으로 상태 전이 규칙(`이미 처리된 요청은 다시 수락할 수 없다` 등)을 검증하고, Service 테스트는 조회·저장과 도메인 간 협력 흐름만 검증하도록 재구성해 TDD(Test-Driven Development, 테스트 주도 개발)를 적용할 수 있는 기반을 마련했습니다.

#### 3. 데이터 위치가 아닌 기능 책임을 기준으로 협력 재설계

기존 사용자 검색 Repository가 `QFriendRelationJpaEntity`를 직접 참조하던 문제를 해결하기 위해, [친구 검색 책임 분리 커밋](https://github.com/ImHereOfRati/server/commit/e9f0f76b6b0b48c7c22cca3610349127c6676fad)에서 친구 후보 검색 흐름을 `friends` 모듈의 `FriendCandidateSearchService`로 옮겼습니다.

```kotlin
class FriendCandidateSearchService(
    private val friendRelationQueryRepository:
        FriendRelationQueryRepository,
    private val userLookupContract:
        UserLookupContract,
) {
    fun search(
        requesterId: UUID,
        keyword: String,
        pageable: Pageable
    ): Slice<UserResult> {
        val excluded =
            friendRelationQueryRepository
                .findRelatedUserIds(requesterId) + requesterId

        return userLookupContract
            .searchActiveByKeyword(keyword, excluded, pageable)
    }
}
```

`friends`가 기존 친구 관계를 조회해 제외할 사용자 ID(Identifier) 목록을 계산하고, `user`의 공개 계약인 `UserLookupContract`를 호출해 활성 사용자를 검색합니다. **사용자 데이터는 `user`가 소유하지만 친구 후보를 추리는 기능은 `friends`가 책임진다**는 기준을 세워 두 모듈 사이의 양방향 영속성 결합을 끊었습니다.

#### 4. 모듈 소유권 유지(`@NamedInterface`)와 명시적 계약 호출

- **책임 있는 모듈의 소유권 유지**: 가장 많이 반복 참조되던 인증 사용자 정보 타입 `ImHereUserDetails`는 여러 모듈의 Controller가 쓴다는 이유로 공용 모듈로 빼지 않고, 인증 책임을 가진 `auth` 모듈(`auth.security.shared`)에 둔 채 `@NamedInterface`로 공개했습니다. [모듈 경계 리팩터링 커밋](https://github.com/ImHereOfRati/server/commit/ad39b9c1373d57a32ad1e00b3ebd34e18837dc8f) 하나로 내부 타입 참조 위반 84건이 즉시 해소됐습니다.
- **불필요한 이벤트 결합 제거**: 필수 약관 동의 후 사용자 활성화를 처리하던 `RequiredAgreementsSatisfied` 이벤트는 두 작업이 한 트랜잭션으로 묶여야 하는 단일 흐름임에도 의존 방향을 숨기고 있었습니다. [같은 커밋](https://github.com/ImHereOfRati/server/commit/ad39b9c1373d57a32ad1e00b3ebd34e18837dc8f)에서 이벤트를 걷어내고 `AgreementService`가 `UserActivationContract`를 생성자 주입받아 명시적으로 호출하도록 변경했습니다.

### 자동 검증의 실제 효과: 사람이 검수하고도 놓친 순환 의존 차단

내부 참조 위반 224건과 순환 의존 7건을 모두 0건으로 만든 뒤 `ApplicationModules.verify()`를 main 배포 워크플로에 활성화했습니다. 그 결과 **AI 에이전트가 수정하고 제가 직접 육안 검수까지 마친 코드에서 아키텍처 위반 2건을 배포 전에 실제로 차단했습니다.**

대표적인 사례가 회원 탈퇴 API(Application Programming Interface)에 `AllowPendingUser` 애너테이션을 적용할 때 발생한 순환 의존입니다. `user` 모듈의 Controller가 `auth` 모듈 내부의 애너테이션을 참조하면서, 이미 사용자 정보 조회를 위해 `auth → user` 의존이 있던 상태에서 `auth → user → auth` 순환 의존이 만들어졌습니다. 기능 테스트와 육안 검수에서는 놓쳤으나 배포 파이프라인의 Spring Modulith 경계 검사에서 즉시 실패했습니다.

해당 애너테이션은 특정 도메인 로직이 아니라 여러 모듈에서 쓰는 공통 접근 제어 표시였기 때문에 [AllowPendingUser 위치 변경 커밋](https://github.com/ImHereOfRati/server/commit/6932e1233fdb63734245906f7ca393d10f3185b3)에서 공용 모듈로 옮겨 역방향 의존을 해결했습니다.

### 결과와 한계

- **내부 참조 위반 224건 및 순환 의존 7건 전량 해소**: `ImHereUserDetails` 공개 범위 조정(84건 해소)과 친구 검색 책임 분리 등 반복 위반의 공통 원인을 해결해 모든 경계 위반을 0건으로 만들었습니다.
- **배포 전 아키텍처 위반 2건 실제 차단**: 육안 검수에서 놓친 `auth ↔ user` 순환 의존 등 경계 위반 2건을 main 배포 전에 막았습니다.
- **도메인 단독 테스트 확보 및 기존 동작 보존**: 도메인 객체만으로 비즈니스 규칙을 검증하는 단위 테스트를 구축했고, 리팩터링 전후 전체 686개 테스트 통과로 대규모 구조 변경 중에도 기존 기능 동작이 보존됨을 확인했습니다.
- **감수한 한계**: 초기 위반 224건을 분석해 재배치하는 비용이 들었으며, 모듈 경계 검사가 통과하더라도 Service에 비즈니스 로직이 몰리는 문제까지 도구가 대신 막아주지는 않으므로 객체 간 책임 배치는 개발자가 계속 판단해야 합니다.

### 다시 한다면

- **도구 적용보다 도메인의 책임과 경계를 먼저 정의하겠습니다**: 위반을 먼저 검출해 하나씩 쫓아가기보다 각 도메인이 맡을 비즈니스 개념과 공개 인터페이스를 먼저 정의한 뒤 검증 규칙을 적용해 시행착오를 줄이겠습니다.
- **Spring Modulith 대신 ArchUnit으로 필요한 규칙만 직접 정의하겠습니다**: 이 프로젝트에 필요한 핵심 제약(타 도메인 JPA 엔티티·Repository 직접 참조 금지, 순환 의존 금지, 계층 간 의존 방향 준수)은 ArchUnit 테스트 클래스 하나로 명확히 표현할 수 있음을 확인했고, 이후 팀 프로젝트(비비디, [사례 4](/cases/archunit-convention))에 이를 실제로 적용했습니다.
- **로컬 AI 에이전트 Hook과 CI(Continuous Integration)에서 이중 검증하겠습니다**: 배포 단계가 아니라 로컬 AI 에이전트 Hook에서 경계 검사를 먼저 실행해 AI가 위반을 즉시 수정하게 만들겠습니다.
