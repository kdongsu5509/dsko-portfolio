### 문제 상황: 모든 질문에 같은 상위 모델을 사용하는 구조

비비디(Bibbidi)는 사용자의 결혼 준비 상태를 바탕으로 할 일을 추천하고 체크리스트와 일정을 관리하도록 돕는 AI(Artificial Intelligence) 챗봇을 제공합니다. 초기에는 추천 기능을 빠르게 구현하는 데 집중해 별도의 Tool Calling 없이 매 요청마다 DB(Database)에서 사용자 정보와 체크리스트를 조회해 프롬프트에 넣었습니다. 이후 체크리스트 변경, 일정 생성·수정 등 챗봇이 수행할 작업을 Tool Calling으로 확장하면서 비용과 응답 시간이 중요한 과제가 됐습니다. 당시에는 인사나 단순한 용어 설명부터 여러 조건을 비교해야 하는 질문까지 상위 모델(`Sol`) 하나로 처리해 간단한 질문에도 비싼 모델을 호출하고 있었습니다.

시스템 프롬프트를 보강하는 과정에서도 한계가 드러났습니다. 57개 시나리오와 8개 평가 지표를 사용한 기존 평가에서 프롬프트 수정 후 실패 시나리오는 12개에서 6개로 줄었으나, 입력 토큰 사용량이 **23.6% 증가**했고 전체 평가 시간도 **18분 38초에서 26분 57초**로 늘어났습니다. 프롬프트 보강만으로 답변 품질을 높일 수는 있었지만 그만큼 토큰과 처리 시간이 더 소모됐습니다.

여기에 데모데이에서 사용자가 `"김치찜 레시피를 알려줘"`라고 요청하자 챗봇이 그대로 레시피를 답변하는 문제도 겪었습니다. 결혼 준비 서비스였지만 기존 시스템 프롬프트만으로는 서비스 범위를 벗어난 요청을 충분히 통제하지 못했습니다. 이 경험을 바탕으로 세 가지 문제를 해결하고자 했습니다.

- 질문 난이도에 비해 과도한 비용이 발생하는 단일 상위 모델 호출 구조
- 시스템 프롬프트만으로는 충분히 차단되지 않는 도메인 이탈과 악의적인 요청
- 여러 모델과 Tool Calling을 함께 쓰는 환경에서의 스트리밍 격리 및 안전한 장애 재시도

### 해결: Jev로 분류하고 질문 난이도에 따라 모델 선택

#### 1. 모든 질문을 상위 모델에 보내지 않도록 난이도별 모델 분기

응답 생성 모델을 호출하기 전에 Jev로 질문을 먼저 분류하고 그 결과에 따라 세 가지 모델 중 하나를 선택하도록 [라우팅 구조(PR #661)](https://github.com/woowacourse-teams/2026-bibbidi/pull/661)를 구현했습니다.

| 난이도 | 모델 | 대상 질문 |
| --- | --- | --- |
| `LOW` | Qwen | 인사, 용어 설명 등 조건이 거의 없는 단순 질문 |
| `MEDIUM` | Luna | 한두 가지 조건을 반영하는 일반적인 상담·추천 |
| `HIGH` | Sol | 여러 조건의 우선순위 판단, 사용자 상태와 이전 대화 비교 |

예를 들어 `"상견례가 뭐야?"` 같은 질문에 복잡한 추론이 가능한 상위 모델을 쓸 필요는 없습니다. 반면 예산과 일정, 현재 준비 상태를 종합해 우선순위를 정하는 질문에는 높은 추론 능력이 필요합니다. 모든 요청을 한 모델로 처리하는 대신 **질문을 해결하는 데 필요한 수준의 모델을 선택하는 것**을 목표로 삼았습니다.

분류를 맡는 Jev는 별도 외부 모델로 구성했습니다. 각 모델의 공개 가격과 응답 속도 자료를 비교해 분류 목적에 필요한 비용과 지연 시간이 낮은 모델을 골랐습니다. AWS(Amazon Web Services)의 모델 라우팅 기능도 검토했으나 당시 사용하려던 서로 다른 모델 계열을 요구사항에 맞게 조합할 수 있는지 확인되지 않아 Jev 기반 분류를 직접 구현했습니다.

#### 2. 난이도·프롬프트 인젝션·태스크 하이재킹을 단일 호출로 검사

Jev에는 질문 난이도 판별만 맡기지 않고 한 번의 요청으로 세 가지를 동시에 판단하도록 [분류 범위를 확장(PR #730)](https://github.com/woowacourse-teams/2026-bibbidi/pull/730)했습니다.

1. **난이도 분류**: `LOW`, `MEDIUM`, `HIGH` 중 응답 생성 모델 선택
2. **프롬프트 인젝션 탐지**: 기존 지침을 무시하거나 도구를 부적절하게 호출하도록 유도하는 요청 확인
3. **태스크 하이재킹 탐지**: 결혼 준비라는 맥락을 빌려 서비스 범위 밖의 작업을 요구하는지 확인

세 검사를 개별 호출로 분리할 수도 있었지만 외부 모델 API(Application Programming Interface)를 각각 부르면 네트워크 I/O(Input/Output)가 그만큼 늘어나므로 단일 Jev 호출로 통합했습니다(네트워크 호출 횟수 감소는 설계상 기대 효과이며 분리 호출과의 실제 지연 시간 차이를 별도 측정하지는 않았습니다). 분류 결과 위험한 요청으로 판정되면 응답 생성 모델을 호출하기 전에 즉시 차단했습니다. 기존 답변 모델의 시스템 프롬프트에도 서비스 범위와 안전성 지침을 그대로 두어 Jev를 기존 방어를 대체하는 수단이 아니라 앞단에 추가하는 방어 계층으로 활용했습니다.

#### 3. 불확실한 분류와 분류기 장애 처리

초기 운영에서는 Jev의 난이도 분류 확신도가 `0.7`보다 낮으면 한 단계 높은 모델을 선택하도록 구현했습니다. `0.7`은 실험으로 최적화한 임계값이 아니라 경험적으로 정한 초기 기준이며, 분류가 불확실할 때 모델 비용을 조금 더 쓰더라도 답변 품질 저하를 막으려는 판단이었습니다.

Jev 호출 자체가 실패하거나 API 키가 없는 경우에는 요청을 차단하지 않고 `HIGH`(`Sol`) 모델을 선택했습니다. 분류기 장애만으로 사용자 질문이 부적절하다고 단정할 수 없었기 때문에 기존 시스템 프롬프트의 방어 지침을 유지한 상위 모델이 처리하도록 넘겼습니다. 다만 Jev 장애 시에는 사전 안전성 검사가 생략되어 기존 시스템 프롬프트에만 의존해야 하는 한계가 있었습니다.

이후 도메인 이탈과 인젝션 검사에서는 실제 우회 사례를 검토한 뒤 [차단 정책을 강화(PR #762)](https://github.com/woowacourse-teams/2026-bibbidi/pull/762)했습니다. 유효한 위험 범주로 분류된 요청은 확신도가 `0.7`보다 낮다는 이유만으로 정상 요청으로 풀어주지 않도록 수정했습니다. 위험 요청을 놓치지 않으려는 선택이었으나 정상 질문을 잘못 차단할 가능성도 함께 커지는 결정이었습니다.

### 악의적인 요청 차단과 정상 질문 오차단 사이의 트레이드오프

데모데이에서 발생한 김치찜 레시피 요청은 프롬프트 인젝션이 아니라 서비스 범위를 벗어난 일반 지식 요청이었습니다. 이 사례를 포함해 직접 작성한 공격 시나리오 9건과 실제 도메인 이탈 사례 1건을 시험해 **총 10건을 모두 차단**했습니다.

이어서 결혼식 일정을 핑계로 요리 절차를 작성하게 하거나 피로연 자료라는 이유로 무관한 일반 지식을 설명하게 하는 등 결혼 준비 맥락으로 포장한 요청([Issue #759](https://github.com/woowacourse-teams/2026-bibbidi/issues/759))도 추가로 검토했습니다. 초기에는 이런 요청을 도메인 이탈로 분류하고도 확신도가 낮아 통과시키는 사례가 있었기에, 분류 기준을 질문의 겉보기 맥락이 아니라 **사용자가 최종적으로 요구하는 작업과 산출물**에 집중하도록 다듬었습니다.

다만 실제 운영에서는 정상적인 결혼 준비 용어를 묻는 질문(예: `"상견례가 뭐야?"`)이 간헐적으로 차단되는 문제도 발생했습니다. 팀 내부 논의 끝에 당시에는 최우선으로 수정할 만큼 치명적인 불편은 아니라고 보아 정책을 유지했지만, 정상 요청을 거부하면 챗봇에 대한 사용자 신뢰가 떨어질 수 있다는 한계가 분명히 존재합니다. 차단 성공 사례 10건은 확인했으나 정상 질문 전체에 대한 오차단율을 정량 측정하지 못해 방어 성능을 종합적으로 입증하지는 못했습니다.

### 모델 실패 시 부작용 없이 안전하게 재시도하는 구조

외부 AI 모델은 언제든 호출 실패나 응답 중단이 일어날 수 있습니다. 특정 모델 장애가 전체 사용자 요청 실패로 이어지지 않도록 선택한 모델이 실패하면 나머지 모델을 순서대로 최대 한 번씩 시도하는 폴백(Fallback) 구조를 만들었습니다.

| 최초 선택 등급 | 장애 시 재시도 순서 |
| --- | --- |
| `LOW` | `LOW → MEDIUM → HIGH` |
| `MEDIUM` | `MEDIUM → HIGH → LOW` |
| `HIGH` | `HIGH → MEDIUM → LOW` |

하지만 단순히 다른 모델을 다시 호출하는 것만으로는 안전하지 않았습니다. 스트리밍 응답과 Tool Calling의 부작용을 막기 위해 재시도를 즉시 포기해야 하는 경계를 명확히 정의했습니다.

#### 1. SSE 응답 전송 이후에는 재시도 금지

챗봇은 답변을 SSE(Server-Sent Events)로 스트리밍합니다. 앞선 모델이 답변 일부를 사용자에게 전달한 뒤 실패했을 때 다른 모델의 답변을 뒤에 이어 붙이면, 클라이언트는 서로 다른 두 모델이 생성한 문장이 뒤섞인 깨진 답변을 받게 됩니다. 따라서 첫 번째 답변 조각이 전달된 이후에는 다른 모델로 재시도하지 않도록 막았습니다.

#### 2. Tool Calling 쓰기 작업 이후에는 재시도 금지

더 위험한 상황은 Tool Calling으로 실제 DB 데이터가 변경된 뒤 응답 생성이 실패하는 경우입니다. 예를 들어 챗봇이 사용자의 일정을 생성한 직후 응답 스트림이 끊겼을 때 다른 모델이 처음부터 요청을 다시 처리하면 동일한 일정이 중복 생성됩니다. 쓰기 도구 실행 중 예외가 발생하더라도 실제 DB 반영 여부를 단정할 수 없는 경우가 있으므로 예외 발생만으로 재시도하는 것도 위험합니다.

이에 **체크리스트·일정 변경 등 쓰기 도구를 한 번이라도 실행한 이후에는 다른 모델로 재시도하지 않도록 제한**하고, 부작용이 없는 조회 도구만 실행한 경우에만 재시도를 허용했습니다. 실제 중복 변경 사고가 터진 뒤 수습한 것이 아니라 예상 가능한 부작용을 사전에 차단하기 위해 설계한 규칙입니다.

#### 3. 자동화 테스트로 재시도 조건 검증

[`SpringAiConversationFallbackTest` 포함 PR #712](https://github.com/woowacourse-teams/2026-bibbidi/pull/712)에서 의도적으로 모델 실패를 일으켜 다음 8가지 조건을 자동화 테스트로 검증했습니다.

- `LOW` 실패 후 `MEDIUM`에서 정상 응답
- `MEDIUM`과 `HIGH`가 연달아 실패한 후 `LOW`에서 정상 응답
- 세 모델이 모두 실패하면 지정된 오류 반환
- 일부 답변 조각을 SSE로 전송한 뒤 실패하면 재시도하지 않음
- 체크리스트·일정 관련 **7가지 쓰기 작업** 실행 이후에는 재시도하지 않음
- 쓰기 서비스에서 예외가 발생해 반영 결과를 확정할 수 없어도 재시도하지 않음
- 조회 작업만 실행한 경우에는 다음 모델로 재시도 허용
- 재시도 성공 시 실패한 모델의 대화가 아니라 최종 성공한 모델의 대화만 메모리에 유지

#### 4. 라우팅·소요 시간 기록과 SSE 응답 전달의 분리 (`Reactor Sink`)

선택된 모델 등급과 응답 소요 시간, 대화 내용을 DB에 기록하는 작업을 사용자 SSE 응답 경로에 그대로 묶으면 기록 지연이나 실패가 실시간 스트리밍 전달에 영향을 줄 수 있었습니다. 이를 분리하기 위해 AI 응답 `Flux`를 `ChatTurn`(`Sink`)으로 공유하고, `ClientSubscriber`는 SSE 답변 전달만 담당하고 `ArchiveSubscriber`는 별도 스케줄러에서 선택된 모델·소요 시간·대화 내용을 비동기로 기록하도록 구현했습니다. 사용자가 직접 변경한 체크리스트·일정과 달리 대화 이력은 보조 데이터라고 판단해 일부 기록 유실 가능성을 감수하더라도 실시간 응답 전달 경로를 우선했습니다(단, `Sink` 도입 전후의 응답 시간 차이는 별도 측정하지 않았습니다).

### 결과: 답변 생성 비용 23% 감소(Jev 제외), 전체 TTFT는 거의 동일

#### 1. 비용 측정 조건과 결과

- **평가 데이터셋 및 단가 기준**: 결혼 준비 상담·추천·Tool Calling을 포함한 **57개 평가 시나리오(8개 평가 지표)**를 분기 전(단일 상위 모델 `Sol`)과 분기 후(`Qwen`·`Luna`·`Sol` 라우팅)에 동일하게 실행해 수집한 입출력 토큰 수에 2026년 10월 기준 각 모델의 공개 토큰 단가를 적용했습니다.

| 항목 | 분기 전 (`Sol` 단독) | 분기 후 (`Qwen`·`Luna`·`Sol`) |
| --- | --- | --- |
| 57개 시나리오 답변 생성 모델 추정 비용 | `$0.74` | `$0.57` |
| 비용 감소율 (Jev 분류 비용 제외) | - | **약 23% 감소** |

모든 요청을 상위 모델로 처리하는 대신 질문 난이도에 맞는 모델을 선택해 답변 생성 모델의 추정 비용을 낮췄습니다. 다만 이 수치에는 **앞단 Jev 분류 호출 비용이 포함되어 있지 않습니다.** Jev 관리 콘솔에서는 누적 `3,211회` 요청, `7,209,134토큰`, 약 `$0.28`의 사용 비용이 확인됐으나 여러 API 키를 통한 운영·팀 테스트·평가 요청이 섞인 전체 기간 누적치라 57개 시나리오 평가 1회 실행의 Jev 비용만 분리할 수 없었습니다. 따라서 Jev를 포함한 시스템 전체의 순절감률은 별도로 주장하지 않습니다.

#### 2. 응답 시간(TTFT) 측정

모델 분기 이후 간단한 질문에서는 평균 `0.88초`의 TTFT가 관측됐습니다. 그러나 전체 평균 TTFT는 **`3.24초`에서 `3.20초`로 거의 달라지지 않았습니다.** 초기에는 TTFT 3초 이내를 목표로 잡았으나 모델의 응답 특성과 앞단 Jev 분류 호출에 걸리는 시간을 충분히 고려하지 못한 목표였으며, 분기 전 42턴과 분기 후 94턴 표본에는 팀 테스트와 서로 다른 Tool Calling 구성이 섞여 있어 엄밀한 동일 조건 비교에는 한계가 있습니다.

#### 3. 답변 품질과 안전성 검증 요약

기존 LLM(Large Language Model, 대규모 언어 모델) as a Judge 평가 체계를 활용했지만 모델 분기 전후를 동일 조건으로 비교한 품질 점수는 확보하지 못했습니다. 또한 직접 작성한 공격 시나리오 9건과 도메인 이탈 1건(총 10건)을 차단한 소규모 테스트만으로는 전반적인 방어 성능을 입증할 수 없으며, 정상 질문 오차단율도 측정하지 못했습니다.

- **확인한 성과**: 57개 시나리오 동일 평가 기준 답변 생성 모델의 추정 비용 약 23% 감소 (`$0.74 → $0.57`, Jev 분류 비용 제외)
- **자동화 테스트 완료**: 모델 실패 시 폴백 순서 및 SSE 전송·7종 쓰기 작업 이후 재시도 금지 8가지 조건 검증
- **소규모 시나리오 확인**: 도메인 이탈 및 공격 시나리오 10건 차단 확인 (단, 운영 중 `"상견례가 뭐야?"` 등 정상 질문 오차단 발생)
- **달성하지 못한 목표**: 전체 평균 TTFT의 유의미한 단축 (`3.24초 → 3.20초`)
- **남은 검증 과제**: Jev 비용을 포함한 총비용 비교, 동일 조건 답변 품질 비교, 정상 질문 전체에 대한 오차단율 측정

### 회고: 기술의 기능뿐 아니라 학습 비용과 부작용 통제도 설계의 일부

이번 작업을 거치며 모델 라우팅과 비용 절감뿐 아니라 Reactor 기반 스트리밍 제어와 Tool Calling의 부작용 통제까지 직접 다뤘습니다. 그중 가장 많은 시간을 쏟은 영역은 Reactor였습니다. Spring AI를 쓰면서 `Flux` 스트리밍과 `Sink` 기반 비동기 분리를 구현할 수 있었지만, 구독과 스케줄링, 오류 전파 방식을 정확히 이해하는 데 예상보다 긴 시간이 걸렸고 구현 속도도 늦어졌습니다.

다시 개발한다면 Spring AI 도입을 당연한 전제로 두지 않겠습니다. 필요한 모델 호출, 스트리밍, Tool Calling 요구사항을 먼저 정의한 뒤 Spring AI를 쓰는 방식과 모델 API를 직접 호출하는 방식을 비교해, 프레임워크가 제공하는 기능뿐 아니라 **팀이 감당해야 할 학습 비용과 구현 복잡도**까지 기술 선택 기준에 넣겠습니다. 측정 역시 전체 평균 TTFT만 보지 않고 `LOW`·`MEDIUM`·`HIGH` 난이도별 TTFT와 Jev 포함 총비용, 정상 질문 오차단율을 동일한 평가 데이터셋 위에서 비교하겠습니다.

무엇보다 **비용이 낮은 모델을 고르는 일만큼이나 어떤 요청을 앞단에서 차단하고 어느 시점부터 재시도를 포기해야 하는지 결정하는 일이 AI 백엔드 설계의 핵심 책임**이라는 점을 배웠습니다.
